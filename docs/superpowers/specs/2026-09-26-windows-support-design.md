# Windows support design

## Decision

Make Concord's production code paths run correctly on native Windows (cmd.exe/PowerShell, no WSL/Git Bash required): the Codex plugin's hook manifest, the shared spawn call sites for `codex`/`git`/`claude`/`copilot`, and JSONL/diff line parsing. Centralize the spawn fix in one shared helper (`core/spawn-cross-platform.js`) mirrored across the three packaged plugin copies, rather than patching each call site's options object independently with duplicated logic.

## Evidence: two of three originally-scoped fixes were false premises

The ticket's evidence sweep (a static grep across the plugin sources) flagged three "hosts don't run hooks correctly on Windows" items by pattern-matching `${VAR}` and `sh -c` syntax. Before implementing, each host's actual hook-dispatch mechanism was traced instead of trusting the pattern match:

- **`plugins/concord/hooks/hooks.json` (Claude Code plugin): no defect, no change.** Claude Code's own hook docs (code.claude.com/docs/en/hooks) state it has no per-platform `"windows"` key at all, and that `${CLAUDE_PLUGIN_ROOT}` is substituted by Claude Code itself as a plain string before the command runs -- not by a shell. The substituted command (`node "<path>"`) has no bash-only syntax, so it already runs correctly whether Windows resolves the shell form to Git Bash or PowerShell. The existing pattern here is the officially documented cross-platform-safe form.
- **`plugins/concord-codex/hooks.json` (Codex CLI plugin): real defect, different fix than originally scoped.** Codex's hook-handler schema (`codex-rs/config/src/hook_config.rs`, `HookHandlerConfig::Command`) defines a `commandWindows` field -- confirmed directly in Codex's source, not just its docs -- as the per-hook Windows override, the same role concord-copilot's `"windows"` key plays for its own host. The existing `command` value is a POSIX `sh -c` script with no Windows equivalent, so this manifest needed a real fix: add `commandWindows` per hook entry, resolving `node` and the target script via PowerShell instead of trying to make the `sh -c` wrapper itself portable.
- **`plugins/concord-copilot`'s hooks.json: no defect, reference precedent only.** Already carries the correct `"windows"` key; this is the pattern the concord-codex fix above follows.

The POSIX `sh -c` script it replaces falls back through `$NVM_BIN`, a POSIX nvm versions directory, Homebrew, and `/usr/local`/`/usr/bin` when `node` is not on PATH (Codex spawns hooks with a scrubbed PATH). The `commandWindows` PowerShell form mirrors that with `Get-Command node` plus one fixed fallback (`$env:ProgramFiles\nodejs\node.exe`, the default location for both the official Windows installer and nvm-windows's PATH-visible symlink) -- narrower than the POSIX script's multi-location search, but covering the common Windows install shapes rather than only the PATH-visible case.

Residual exposure: `commandWindows`'s correctness against a real Codex-on-Windows host is unverified (no Windows machine available). Verification here is schema/content-level (`commandWindows` is present, non-empty, references the right target script, and never shells out to `sh`/`bash`) -- see `plugins/concord/hooks/test/codex-hooks-windows.test.js`. Whoever first runs Concord's Codex plugin on native Windows should treat this as the first real-world check of that field, not an already-proven path.

## Spawn helper

`core/spawn-cross-platform.js` exports `crossPlatformOpts(opts)`, which adds `shell: true` to child_process options only when `process.platform === 'win32'`, otherwise passing options through unchanged. Applied at every `spawn`/`execFileSync` call site for `codex`, `git`, `claude`, and `copilot` in `core/target.js`, `core/codex-review-runner.js`, and `core/review-cli.js` (its own separate `sh()` helper for `git add`/`commit`/`checkout --`/`merge-base`/`show`/`status`/`rev-list`, distinct from `target.js`'s `sh()`) -- and their byte-identical mirrors in `concord-codex/engine/` and `concord-copilot/engine/`.

Trade-off found and closed, not just disclosed -- an earlier draft of this note first overstated Node's escaping behavior, then, after correcting that, still understated the resulting gap's severity. Node's own docs state that when the resolved Windows shell is cmd.exe, `windowsVerbatimArguments` is forced to `true` regardless of what the caller passes -- Node performs **no** quoting or escaping of `args` in that case. A first pass at this note treated that as a narrow risk limited to a literal `"` in a reviewer prompt or commit message. `review-until-green`'s own correctness review on this diff (round 1) caught the real blast radius: with zero quoting, Node joins `[command, ...args]` with plain spaces before handing the line to cmd.exe, so ANY argument containing a space -- not just a quote or another cmd.exe metacharacter -- splits into multiple argv entries. That hits `stateDir`/`repoRoot` path arguments at nearly every call site this fix touches (`--add-dir <stateDir>`, `--cd <repoRoot>`, `-C <repoRoot>`), and a default Windows user-profile path routinely contains a space ("C:\Users\Jane Doe\...", "Program Files"). This was the common case, not the rare one.

Fix: `spawn-cross-platform.js` also exports `crossPlatformArgs(args)`, applied alongside `crossPlatformOpts` at every one of the same call sites. On win32 it quotes each argument per the documented CommandLineToArgvW rule (the same argv-splitting algorithm every Windows child process' own C runtime startup applies to its command line): wrap in `"..."` when the argument contains a space, tab, or `"`; double a backslash run immediately before an embedded `"` (escaping it as a literal quote) and double a trailing backslash run before the closing quote (so it can never accidentally escape that quote); every other character, including cmd.exe metacharacters, passes through literally inside the quotes. `quoteArgumentForWindows`'s input/output pairs are covered by `spawn-cross-platform.test.js` against the documented rule (a space, an embedded quote, backslash-before-quote, a trailing backslash, and the empty-argument case) -- verifiable as a pure string transform without a live Windows host, unlike the residual gap below.

Residual gap, disclosed rather than attempted: this closes argv-splitting (the CommandLineToArgvW layer), but not cmd.exe's own, separate command-line parsing -- its `%VAR%` expansion and `&`/`|`/`^`/`<`/`>` operators are interpreted by cmd.exe before the argument even reaches CommandLineToArgvW, and wrapping in quotes does not fully suppress that in cmd.exe the way it would in a POSIX shell. A second round-1 correctness pass flagged a specific instance of the same layer: `codexExec`'s reviewer/fixer `prompt` argument routinely contains a literal newline, and it is untested whether cmd.exe's own command-line reader treats an embedded newline as a command terminator/separator the way it does for a batch-file line, distinct from (and not protected by) the CommandLineToArgvW quoting `crossPlatformArgs` already applies. Closing this layer -- `%`/`&`/`|`/`^`/`<`/`>`/embedded newlines, and any other cmd.exe-parser-level character -- correctly needs a real Windows host to verify against (getting it wrong -- e.g. mangling a legitimate `%` inside a path, or corrupting a prompt by escaping a newline that didn't need it -- could be worse than the current, disclosed gap), which this repo does not have. A reviewer prompt or commit message containing any of these, including a multi-line prompt, is the next thing to test on a real Windows host, not an already-solved case.

## Gate-review findings (branch-diff review, round 1)

Two coverage gaps a diff-local reviewer cannot see, both caught by `review-until-green`'s broad gate pass on this branch and fixed:

- `plugins/concord-codex/bin/review-until-green.js` calls `execFileSync('git', ['branch', '--show-current'], ...)` directly to default the target ref when none is given, unwrapped by `crossPlatformOpts`/`crossPlatformArgs` -- every other git/codex/claude/copilot call site in the shared `core/` (and its `concord-codex`/`concord-copilot` mirrors) got the fix, but this CLI entry point's own inline call was outside that sweep. Fixed the same way as every other call site.
- `plugins/concord/hooks/test/codex-bundle-drift.test.js` asserts `concord-codex/engine/` stays byte-identical to `core/` (including the new `spawn-cross-platform.js`), but no equivalent test existed for `concord-copilot/engine/`, even though `concord-copilot/bin/bundle.mjs` vendors the exact same core files into its own `engine/`. All 3 files were already byte-identical when checked; nothing would have caught future drift there. Added `plugins/concord/hooks/test/copilot-bundle-drift.test.js`, mirroring the codex one for copilot's own vendored-adapter file set (`event.js`/`statedir.js`; copilot has no vendored `transcript.js`, unlike codex's `event.js`/`statedir.js`/`transcript.js`).

## CRLF line-splitting

Fixed `split('\n')` -> `split(/\r?\n/)` in `core/review-cli.js`, `core/extract.js`, and `adapters/claude-code/review-telemetry.js`. The original evidence sweep's framing ("CRLF breaks JSON.parse") was imprecise: `JSON.parse` already tolerates a trailing `\r` per the JSON grammar (verified empirically: `JSON.parse('{"a":1}\r')` succeeds). The real, narrower defect is in `review-telemetry.js`'s `.filter(Boolean)`/`.find(Boolean)` calls -- a genuinely blank line in a CRLF file becomes the string `'\r'` after splitting on `'\n'` alone, which is *truthy* and therefore survives the filter, then fails `JSON.parse('\r')` ("Unexpected end of JSON input"). Splitting on `/\r?\n/` turns that blank line into `''`, which `Boolean` correctly drops.

`adapters/claude-code/transcript.js`, `adapters/codex/transcript.js`, and `concord-codex/engine/transcript.js` also split on `'\n'` but were left unchanged: each result line is immediately `.trim()`med before `JSON.parse`, which already strips a trailing `\r`, so there is no discriminating red there.

## Non-goals (explicit, from the approved ticket)

Windows CI; rewriting the Unix-only test fixtures -- the `fs.symlinkSync` fixture and `sh`/`bash` `spawnSync` fixtures in `codex-event.test.js`, and the `chmodSync` "executable"-permission (mode `0o755`) fixtures in `codex-review-runner.test.js` and `e2e-file-target.test.js` (different files; `codex-event.test.js` itself has no `chmodSync` calls). `plugin-version.test.js` also calls `chmodSync`, but at mode `0o444`/`0o644` to assert the release script fails when it can't write a manifest -- a read-only-attribute fixture, not an exec-bit one; Windows has a partial equivalent for a read-only attribute (unlike the POSIX exec bit, which it has none for), so this one is a smaller, differently-shaped gap grouped here only for "still Unix-permission-flavored, not fixed by this ticket," not because it needs the same fix. `services/agent-team/smoke/container-isolation-verify.mjs` (intentionally Linux/Docker-only); rewriting arbitrary user-authored `review.config.json` shell commands; `fs.chmodSync(stateDir, 0o700)` in `adapters/copilot/statedir.js` (harmless no-op on Windows, not a defect). `codex-transcript.test.js` was checked and does not need this non-goal: its only `bash` occurrence is a literal string inside a JSON test payload, never spawned as a process.
