# Protocol-v2 transactions in production runners and file targets

Protocol v2 plans root-cause groups, fixes each group, certifies the candidate and commits it. Two runners drive it: the packaged runner (`plugins/concord/core/codex-review-runner.js`) and the agent-team service runner (`services/agent-team/src/review_runner.mjs`), and native drivers follow `plugins/concord/core/review-driver.md`. This note fixes the gaps in #166 and #168: the service adapter cannot spawn `plan` or `certify`, the service runner runs every fixer before any certificate, a legitimate no-edit fix ends in a harness failure, a file target can enter a round transaction it cannot certify, plan and certificate identities are not exact, structural evidence is bound only to a hash, and a certified file edit is recorded as `unresolved` in review history.

## Decisions

### Spawn adapter and transaction order

The service spawn adapter builds the `plan`, `fix` and `certify` prompts with `reviewerPrompt` from `plugins/concord/core/round-plan.js`, loaded through `createRequire`, and derives the intent file name with `targetSlug` from `plugins/concord/core/review.js`. The service container ships `plugins/concord`, so both runners send the same prompts and write the artifact names `review-cli` reads; the adapter's own fix prompt and `fixArtifactPath`, which named the artifact by finding id and omitted `groupId`, are removed.

When `round-start` applies the gate, the service runner spawns `gate` with `review` and `gate-verify` after `verify`, before `plan`, as the packaged runner does; without them `plan-fixes` rejects round 1 for a missing gate artifact. The service passes no initiative options, so its `gateMode` is always `pair` and the lite `design-conformance` path, which skips `gate-verify`, does not reach it.

The service runner follows the packaged runner's two paths. A group-scoped plan completes `fix`, `certify` and `commit-fix` for one group before the next group's fixer starts. A round-scoped plan runs every member fixer, then one `certify` and one `commit-fix` for the plan id. The packaged runner skips `commit-fix` for a file target. The service runner reviews only Git targets: the service hands it a Git ref and base (`capability.mjs`), has no file-target entry point, and so has no file-target branch.

### File targets never enter a round transaction

A file target has no Git commit and records fixes per group certificate, so it cannot complete a round transaction. When `plan-fixes` derives `transactionScope:"round"` for a file target, it stops before any fixer with the existing `group-reconcile` packet: `planned` and `fixGroups` are empty, `avoidedLaunches` counts every planned fix, and `record` ends the round as `gate-pending` exactly as for an `action:"reconcile"` group. The packet's reason is `file targets cannot certify a round transaction; groups that share an invariant need a human decision before editing`, and its groups are the structural groups that share an invariant, each with a `reason` naming the shared invariant. When the plan also has reconcile groups, the packet lists both. Reusing the trigger keeps one reconciliation path in `record`, the handoff and the native drivers. `fix_plan.transactionScope` still records `round`, because that is the classification the person reconciles.

### No-edit fixes

A fix artifact `{"status":"ok","edited":false}` is a fixer outcome, not a harness fault. A runner reads each member's fix artifact after its fixer returns; when a group-scoped group or any member of a round transaction reports `edited:false`, it launches no certifier and does not call `commit-fix` for that transaction, and goes on to the next group or to `record`. Certifying an unchanged or partial candidate would spend a reservation on a certificate that cannot authorize anything.

`commit-fix` applies the same rule for a driver that calls it anyway. After its plan, membership and reservation checks, when every member artifact has `status:"ok"` and at least one has `edited:false`, it writes nothing and returns `{"committed":false,"reason":"no edit"}`, or `"incomplete round transaction: no edit for <groupIds>"` when other members of a round transaction edited files. A missing artifact, another status, or an edited artifact with the wrong `groupId` or no files still fails as before.

`record` parks a no-edit member as `needs-decision` with `fix reported no edit or the file was unchanged`. In a round transaction with mixed members, the edited members park with their edit kept in the working tree, the rule [the review artifact contract](review-artifact-contract.md) gives an edited fix without a commit, and the run ends `parked`. A no-edit outcome is never fixed and never a harness failure.

### Group identity

`normalizeArtifact('plan')` in `plugins/concord/core/artifact-contract.js` rejects a plan in which two groups share a `groupId` or share `safeIdForFilename(groupId)`, naming both group indexes. The check sits with the existing `groupId` pattern check because uniqueness is a property of the artifact. `artifact-normalize` repairs only a status spelling or a mixed-namespace id, so it answers this error with `harness-failure` and no representation repair, and the plan is never sealed; `plan-fixes`, which normalizes the same bytes, fails as `invalid v2 classification plan` before it writes the ledger. No fix reservation or edit follows either way.

### Exact sets

One helper in `review-cli.js`, `sameMembers(actual, expected)`, holds when `actual` is an array with no duplicates, has the length of `expected`, and contains every member of `expected`. `commit-fix` uses it for the certificate's `resolvedFindingIds` against the transaction's finding ids and the certificate's `files` against the union of fix files; `record`'s file-target check uses it for `resolvedFindingIds` against the group's finding ids and the certificate's `files` against the fix artifact's `files`. A duplicate can no longer stand in for a missing member. Certificates carry no invariants since #282, so the set checks cover finding ids and files only.

### Structural evidence binding

For a structural `action:"fix"` group, `plan-fixes` reads `<stateDir>/intent-<slug>.md` and accepts the group only when `designEvidence.source` is exactly `intent-<slug>.md`, `designEvidence.sourceHash` equals `ledger.intentHash`, the content hash of the bytes just read equals `ledger.intentHash`, and every requirement occurs in that text after runs of whitespace are collapsed to one space on both sides. The match is otherwise literal and case-sensitive. Re-hashing the bytes it searches proves the requirements came from the approved intent, and collapsing whitespace accepts a quote of a requirement that the intent wraps across lines. Any failure throws `harness-failure` before the ledger is written, as the existing hash check does; the planner retry allowance covers only incomplete classification, and extending it is a policy change outside this work.

### Review history

`record` derives each group's history outcome from the member dispositions it has just computed: `fixed` when every member of the group is in `fixedIds`, otherwise `reconcile` when the round reconciles and `unresolved` otherwise. `fixCommit` is the journal sha for a Git target and `file-edit` for a file target. For a Git target the journal entry is what puts those members in `fixedIds`, so one rule covers both targets and history cannot contradict finding status. The next round's `round-<n>-history.json` is built from `review_history`, so the planner sees a certified file edit as fixed.

### Driver text

`review-driver.md` step 5 and its copy in `plugins/concord/commands/review-and-fix.md` still describe a certificate that attests invariants and file targets limited to singleton groups. Both take the step-5 text below; `bin/bundle.mjs` regenerates the Copilot copy at `plugins/concord-copilot/skills/review-and-fix/references/review-driver.md`. `plugins/concord/skills/review-until-lgtm/SKILL.md` step 3 describes the certifier's check, not the certificate, so it is unchanged.

> 5. For each authorized group, reserve one `fix` launch and apply one coherent change for its complete membership. The fixer MUST write ONLY its result JSON to `<stateDir>/round-<n>-fix-<safe-group-id>.json`: `{"status":"ok","edited":false}`, or `edited:true` with the exact `groupId` and every edited file. When the group reports `edited:false`, launch no certifier and run no `commit-fix` for it; `record` parks its findings as `needs-decision`. Otherwise reserve an independent `certify` launch, and paste the `files` arrays of the group's fix declarations verbatim into its prompt as the edited files to inspect. The certifier checks the actual candidate against every member finding and planned invariant and writes `blocked` unless all of them hold, so its `ok` is the attestation; the certificate itself carries the `groupId`, the exact resolved finding ids, the exact union of edited files with the SHA-256 of each file's current bytes, and focused evidence, never the invariants. It MUST write ONLY its certificate JSON to `<stateDir>/round-<n>-certify-<safe-id>.json`; span disappearance is neither necessary nor sufficient. For `transactionScope:"group"`, run `commit-fix <ref> <groupId>` only after that group's certificate, and finish it before the next group's fixer. For `transactionScope:"round"`, run all group fixers sequentially in the same candidate; when every member edited, certify the complete plan once and run `commit-fix <ref> <planId>` once, and when any member reports `edited:false`, certify and commit nothing. A partial or stale certificate never commits. File targets use explicit groups and certified content but skip the Git commit; `plan-fixes` never gives a file target a round transaction.

## Cost and residual exposure

A planner that reuses a group id ends the run with a harness failure at `artifact-normalize`, or at `plan-fixes` when it receives the same bytes, and a planner that misquotes a requirement ends it at `plan-fixes`; neither gets a representation repair or an automatic replan. A requirement that matches literally can still be quoted out of context; completeness of the quoted requirements stays the planner's responsibility, as #166 states. Certification-request digests, canonical JSON binding and abort or quarantine of cancelled workers remain deferred to #191. File targets cannot fix two structural groups that share an invariant without a person deciding first. The service runner stays limited to Git targets; adding a file-target entry point to the service needs the packaged runner's file-target branch first.

## Executable gates

In the file-target `edited:false` row the codex runner test carries the red, because `record` on `d45032d` already parks that finding `needs-decision` with no `fix_commit`, so `record file target: fix artifact with edited:false parks needs-decision, no fix_commit` passes on both.
