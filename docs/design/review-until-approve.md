# review-until-approve

`review-until-approve` reviews someone else's pull request the way `/review-and-fix` reviews a branch, publishes the verified findings, waits (see Wait for the cost per harness) until the author pushes and replies, reviews what changed, and approves the pull request once a round is clean. It is `/review-and-fix` that never fixes. It never requests changes, merges, pushes to the branch, or posts outside the pull request, and it runs only for a pull request the user named.

## Scope

The skill runs on Claude Code and Codex. It lives in `plugins/concord/skills/review-until-approve/` and is bundled into the Codex package with `plugins/concord-codex/bin/bundle.mjs`, without its `test/` directory, whose helpers the Codex package does not carry. It is not in the Copilot package (tracked in #363). The review runner and the review CLI are found by `scripts/locate.js` in `core/` and `hooks/` (Claude Code) or `engine/` and `bin/` (Codex); `scripts/run-review.js` calls `runReviewUntilGreen` directly, so the Codex bin wrapper needs no `reviewOnly` entry point. It runs the review through `runReviewUntilGreen` in `plugins/concord/core/codex-review-runner.js` with `reviewOnly: true`, the same runner `services/pr-review` uses, so there is no second reviewer implementation. `services/` is not part of the installed plugin, so the skill re-implements the publication contract of `services/pr-review/review-one.sh` (finding format, inline-only-in-hunk rule, body fallback, head re-check, credential refusal) instead of sourcing it.

The decisions below are the conclusions of the Opus design pass.

## Round procedure

| Step | Rule | Reason |
|---|---|---|
| Round 1 | Broad review of the PR head against the merge base, requirements from the PR title and body | Same procedure as `/review-and-fix` |
| Checkout | Fresh full clone in a temporary directory, exact head SHA, review run with an allowlisted environment (`PATH`, locale, proxy and certificate variables, the Codex home for its auth, or for an opted-in Claude reviewer the OAuth token or a copy of the real `.credentials.json`; see the Reviewer row) and an empty `HOME` otherwise. The runner itself runs with that empty `HOME`, so `approve.js` hands the engine the account's real home (`reviewRealHome`) and the real `CLAUDE_CONFIG_DIR` (`reviewDenyRead`). The Codex profile denies every entry of the real home except the way to the checkout, the review's own directories and the Codex binary, so the account's credential files (gh, ssh, cloud, Claude, Codex) are not readable by absolute path. The Claude reviewer has no such restriction | The checkout is untrusted, and a prompt injection could otherwise read a credential file and quote it in a published finding. Checked with a decoy file in the real home: readable to `codex exec` under the old profile, refused under the new one, with `git` and writes into the checkout still working. Entries created in the home after a Codex review starts are not denied |
| Submodules | Each gitlink the pull request changes is checked out at its own path in the review clone, in a fresh `.git` made with `--template=` (no hooks or configuration from the pull request), and `diff.submodule=diff` is set, so the engine's diff holds the submodule's own hunks. `.gitmodules` is read as a git blob; only a GitHub repository qualifies (`https://github.com/O/R`, `git@github.com:O/R`, `ssh://git@github.com/O/R`, `../R`, `../../O/R`), and the fetch url is built from `O/R` by `approve.js`, never taken from `.gitmodules`; `git submodule` is never run. The submodule must be readable by the account and public, or the pull request repository itself (compared by the name GitHub resolves). One level only. A range that fails any of this is recorded on the round as `unreviewed` with the reason `url`, `path`, `unreadable`, `audience`, `fetch` or `nested` (a submodule the pull request adds is checked for nested submodules too); the review says so, is a `COMMENT`, and no approval is posted for that head. The next round reviews the whole pull request again and retries. A removed submodule needs nothing fetched. A finding below a gitlink is verified in the submodule checkout and is posted in the review body, never inline | A gitlink diff is only `Subproject commit` lines, so the reviewer could not judge the change. A `.gitmodules` url is attacker-chosen (`file://`, `ext::`, an option-shaped string), so none of it reaches git. A private submodule would otherwise be quoted into a review its readers may not be allowed to see; collaborators are per repository, so same owner does not mean same readers. The submodule `.git` is writable by an unconfined reviewer, the same exposure the clone's `.git` already has |
| Reviewer | `start` picks the reviewer. An explicit `--reviewer` or a resumed ledger is kept, and `start` refuses when it is not ready, naming what is missing. Without one, the harness's own reviewer runs when it is ready (`claude` under Claude Code, with `CLAUDECODE` set, `codex` otherwise), else the other one, and `start` prints a one-line `note` with the reason (for example `reviewer: codex (claude: pass --allow-unrestricted-home ...)`). Ready means: `codex` is installed and logged in (`auth.json` in the Codex home); `claude` is installed, `--allow-unrestricted-home` was passed, and a login exists (`CLAUDE_CODE_OAUTH_TOKEN`, or a `.credentials.json` in the Claude configuration directory). When neither is ready `start` exits non-zero with one line per reviewer naming the missing piece and writes no ledger. `claude` therefore never runs without the flag, and with it `start` and every round print a warning that the reviewer can read the real home and a malicious pull request could publish what it reads. The opt-in is per `start`; a later `start` without the flag is refused | The Claude reviewer has Bash and an empty `HOME` does not stop an absolute-path read, so its restriction (an operating-system wrapper or settings, verified with a decoy file) is a separate help-wanted issue, not part of this change; the same issue decides how the Claude login reaches a confined reviewer without being readable by its tools. Until then the opted-in reviewer authenticates as the user, which costs nothing the opt-in has not already given up: the token when `CLAUDE_CODE_OAUTH_TOKEN` is set, else a copy of the real `.credentials.json` in the reviewer's own config directory. The user's settings, hooks, plugins and MCP servers never load into the review, because their allow rules and a logged-in `gh` would go beyond what the opt-in accepts; a host that keeps the login outside that file (the macOS keychain) therefore needs the token until a tracked follow-up reads the keychain into the reviewer's own copy. The token values in a credentials file, and in the reviewer's copy of it, are checked against the review text before it is posted. Choosing the other reviewer never weakens a restriction: the fallback is `codex`, which stays confined, or an opted-in `claude` |
| Later round range | `chooseRange`: same merge base and the last head an ancestor of the new head gives `last head..head`; otherwise `merge base..head`; a changed PR title or body gives `merge base..head` with the broad gate | A force push or a merged-in base branch has no isolatable delta; a changed requirement needs the gate again |
| Earlier findings | A finding is `fixed` only on evidence in git objects, never because the reviewer is silent. Each finding records `spanVerified`, the head SHA at which its span occurred byte for byte in the file stored in that head's git object (`git ls-tree` then `git cat-file`, a regular file of at most 20 MiB, never the working tree). A later round compares that head with the new head (`git diff -M --name-status`, one tree comparison however many pushes lie between) and resolves the finding's path through renames. It is fixed when the span no longer occurs at that path or in any other file the diff leaves in place; a deleted file counts as absent. It stays open, with `openReason`, as `unverified` (no verbatim span was ever recorded, which includes an empty span and every finding of a ledger written before this field existed), `span-present` (the span occurs at the path or moved to another file, and the finding follows it), `raised` (the reviewer raised it again) or `path-unresolved` (the old head cannot be fetched, or the path is a symlink or file over 20 MiB at the new head, or below a gitlink whose checkout is missing). `unverified` and `path-unresolved` findings cannot be settled from the code: the `round` output lists them as `held` and says `waive` clears them. Open findings are still passed to the reviewer as guidance (up to 20, with the path after a rename) so it can raise one again under the same id, which keeps it open and not posted again; the guidance decides nothing | The reviewer's silence is a signal a prompt-injected reviewer controls, and the checkout is writable by the reviewer inside the Codex sandbox, so neither can fix a finding. A push that changes only a file mode shows `M` in name-status and the reviewer only a mode line; the span is still there, so the finding stays open. Matching is exact bytes with no whitespace or line-ending normalization, so a span the engine reflowed does not verify and is waived. A fixed finding the reviewer raises again with the span verbatim at the head reopens in place, and a re-raise of an unverified finding with the span verbatim verifies it; a re-raise matching only by id never replaces a span |
| Publication | One review per round, `commit_id` set to the reviewed head, event `COMMENT`, or `APPROVE` when the round is clean. Never `REQUEST_CHANGES` | The clean round's review is the approval |
| Published finding | Key is the hash of the file and the whitespace-collapsed span, or file plus id when the span is empty. A finding already in the ledger is listed as "Still open", not posted again | A span survives an id the model renamed |
| Fixed finding | The next review body carries one line, "Fixed since `<sha>`: ids" | Replying to or resolving another account's threads is out of scope for the first layer |
| First line | `<!-- concord-approve: <head> round:<n> base:<range base> -->` | `services/pr-review/scan.sh` treats a first line starting with `<!-- concord-review` as scheduling evidence, so the skill uses a different prefix |

## Finding locations

Finding-producing reviewer prompts require continuous verbatim source snippets, preserving whitespace and line breaks. Explanatory ellipses and pseudocode are not source anchors. Omissions use a related existing statement in the named file as their anchor.

The skill enables one optional anchor extraction call after the verified review result, through the same provider launch, sandbox, cancellation and protected-artifact boundary. It requests locations for at most 20 findings whose spans do not occur in their committed source. Only regular UTF-8 git blobs up to 1 MiB in the top-level reviewed commit are eligible; findings inside submodules retain their body-only publication and are not re-anchored from checkout contents. The extractor reads the named source and returns an index and a snippet, without changing the finding's identity, file, category, summary or requirement. The runner accepts a correction only when its nonempty snippet is at most 8192 UTF-8 bytes and occurs exactly once in that same committed file. It derives a single-line anchor's line from those bytes. A multiline anchor keeps a null line so the publisher can select the first line of the span overlapping a diff hunk, even when its leading context starts outside the hunk. The original reviewer artifacts remain sealed; the extraction has its own round artifact.

Existing verbatim spans and their engine line numbers remain unchanged. A malformed response, missing or ambiguous correction, unreadable source, or failed extraction preserves the original finding. There is no second extraction attempt and no fuzzy location matching. Checkout or artifact tampering, cancellation and launch-budget denial still stop the run. Inline publication requires the resulting line to be inside a diff hunk; all other findings stay in the review body. A finding whose anchor remains unverified keeps the existing `held` and waiver behavior.

## Approval condition

`evaluateApproval` approves exactly when all of these hold: the reviewed head is the live head, the pull request is open and not a draft, the reviewing account is not the author, no approval was already given for this head, and no finding in the ledger is open. The review engine emits no severity, so every verified finding blocks until it is fixed or the user waives it with the `waive` verb. A waived finding is recorded in the ledger and does not block. A finding the code cannot settle (`unverified`, `path-unresolved`) is cleared only by `waive`, by finding id or, when several open findings share an id, by key.

Required checks are not part of the condition. Approval is a code-review verdict; merge gating belongs to branch protection. A draft is never approved: the skill tells the user, and invoking it again after the pull request is ready approves the unchanged head without a new round.

## Wait

`scripts/watch.js` reads the ledger without writing it, polls `gh` every 60 seconds, prints one JSON event line, and exits. It runs under `mien exec <profile> --` where the reviewing account is not the ambient one.

| Harness | How the session waits | Model cost |
|---|---|---|
| Claude Code | `watch.js --max-wait 6600` as a Bash `run_in_background` command with `timeout: 7200000`, which wakes the session when it exits; on `idle` or a killed run the session runs the same command again | one small model call per window, about 13 a day; the 7-day wait is about 92 windows |
| Codex | `watch.js --max-wait <seconds>` in the foreground; after that many seconds without an event it prints `{"event":"idle"}`, and the session runs it again | about one small model call per window; a window is bounded by the shell tool's command timeout (540 seconds by default in the skill) |

Monitor is not used on Claude Code: it stops after 30 minutes, while a background Bash command runs up to 7200 seconds. The explicit 7200000 ms timeout replaces the 30-minute background default, and 6600 leaves 10 minutes for a poll, `gh` latency and startup, so `idle` is printed before the host kills the command; a killed run is treated like `idle` and a non-zero exit with no JSON line is reported, so a crash is not re-armed in a loop. The session re-runs the identical command it built once with absolute paths and never edits, wraps or replaces `watch.js`. A user stop calls TaskStop on the recorded task id. Codex has no background process that wakes a conversation, so its wait costs the same per window but windows are 540 seconds; the skill tells the user after six idle windows in a row. `<ledger>.watch.json` carries the head seen, the nudge shown and the failed polls in a row from one run to the next, so a new window does not restart the two-poll head stability check, repeat a nudge or hide an outage behind `idle`. A window ends at its deadline: the sleep between polls is cut to the time left. The ledger stays the session's and `approve.js`'s alone.

| Event | Fires when |
|---|---|
| `round` | The head differs from the last reviewed head and the author replied after the last review, and the head was the same on two consecutive polls |
| `merged`, `closed` | The pull request reached that state |
| `nudge` | Only a push, or only a reply, has arrived and 24 hours have passed since the last review. It repeats only for a new head or reply, and posts nothing; the session tells the user |
| `timeout` | 7 days since the last review |
| `idle` | Only with `--max-wait`: the window ended without an event (exit status 0); the session runs the same command again |
| `error` | Ten consecutive failed polls, counted across bounded runs (exit status 1) |

A reply is a comment by the pull request author after the last review, either in a thread of a review the skill published (`in_reply_to_id` is one of its comment ids) or on the pull request conversation, which is the only way to answer a finding posted in a review body. Who pushed does not matter. A push or reply alone, a CI change, a label, or a comment by anyone but the author wakes nothing. A user stop ends the watch and is recorded in the ledger. At most 10 rounds run per pull request, and nothing is posted on any stop.

## State

One JSON file per repository, pull request and reviewing account at `${REVIEW_APPROVE_STATE_DIR:-${CLAUDE_CONFIG_DIR:-~/.claude}/concord/review-until-approve}/<owner>__<repo>__<pr>__<login>.json`, outside any checkout, written atomically, locked by process id so a second session on the same pull request is refused. It holds the reviewing account, the author, `rounds[]` (head, range base, merge base, requirement hash, submission time, review id, comment ids), `findings[]` (key, id, category, file, span, `spanVerified`, summary, status `open|fixed|waived`, `openReason`), `nudged`, `approval`, `stopped`, and `pending` (the head, the newest review id before the post, the round about to be recorded and the findings it would leave, written alone before an `APPROVE` is posted and removed once the review is recorded; the ledger's own findings change only when the review is recorded). What happened since the last review is derived from GitHub on every poll, never stored. Invoking the skill again on a pull request with a ledger resumes it: a moved head runs a round at once, since the invocation is the user's request; otherwise the watch restarts.

## Identity

Every `gh` call, read and write, runs as the account the user names (`mien exec <profile> -- gh`, else the ambient account), recorded as the reviewer. A different account has its own ledger (the login is in the file name) and starts at round 1. If the account is the pull request author, the skill refuses before round 1, because GitHub rejects self-approval. Approval is `POST repos/{o}/{r}/pulls/{n}/reviews` with `event=APPROVE` and `commit_id`, because `gh pr review --approve` cannot pin the commit and races with a push. A push between the last head check and the POST is accepted: the approval is pinned to the reviewed `commit_id`, so GitHub shows it against that commit and branch protection decides whether a later push dismisses it. An account below write permission is warned that its approval will not satisfy branch protection.

## Unattended deployment

The loop can later run unattended, with GitHub Actions or `services/pr-review` reacting to the push and the reply instead of a session's shell loop. The pure decisions (`chooseRange`, `isPublished`, `classifyPrior`, `evaluateApproval`, `repliesSince`, `wakeDecision`) are in `scripts/lib.js`, and the publication code is separate from the watch. Neither depends on Monitor or a live session. No unattended variant is built.

## Residual exposure

- If the `APPROVE` post errors and the head then moves, the pending marker is not settled against GitHub's review list until a later `start`, `round`, `approve` or `waive` reads it; an approval GitHub accepted for the old head stays recorded only on GitHub until then.
- A body-mode retry after a timed-out post can post a second review when GitHub's review list lags behind the first.
- Fixed means the quoted text no longer occurs, not that the defect is gone; a trivial edit inside the span fixes the finding, and the next diff review is what catches a defect that remains. A fix that is later undone is noticed only when the reviewer raises the finding again. A reformat that changes the quoted bytes (re-indent, CRLF) fixes the finding for the same reason.
- A finding for which bounded extraction cannot establish a verbatim span stays unverified and can only be waived. A reviewer that withholds a finding at round 1 is not detectable.
- The review-only state directory is writable by the reviewer (it is the artifact channel); the runner pins and hashes the files it later trusts, so a later role cannot change them unnoticed, but the directory is not read-only.
- The Claude reviewer is not confined (`--allow-unrestricted-home`) and is not trusted to leave the review clone intact beyond the `GIT_NO_REPLACE_OBJECTS` setting; the confinement is tracked in issue #366.
