# review-until-approve

`review-until-approve` reviews someone else's pull request the way `/review-and-fix` reviews a branch, publishes the verified findings, waits (see Wait for the cost per harness) until the author pushes and replies, reviews what changed, and approves the pull request once a round is clean. It is `/review-and-fix` that never fixes. It never requests changes, merges, pushes to the branch, or posts outside the pull request, and it runs only for a pull request the user named.

## Scope

The skill runs on Claude Code and Codex. It lives in `plugins/concord/skills/review-until-approve/` and is bundled into the Codex package with `plugins/concord-codex/bin/bundle.mjs`, without its `test/` directory, whose helpers the Codex package does not carry. It is not in the Copilot package (tracked in #363). The review runner and the review CLI are found by `scripts/locate.js` in `core/` and `hooks/` (Claude Code) or `engine/` and `bin/` (Codex); `scripts/run-review.js` calls `runReviewUntilGreen` directly, so the Codex bin wrapper needs no `reviewOnly` entry point. It runs the review through `runReviewUntilGreen` in `plugins/concord/core/codex-review-runner.js` with `reviewOnly: true`, the same runner `services/pr-review` uses, so there is no second reviewer implementation. `services/` is not part of the installed plugin, so the skill re-implements the publication contract of `services/pr-review/review-one.sh` (finding format, line and file comments, per-comment body fallback, head re-check, credential refusal) instead of sourcing it.

The decisions below are the conclusions of the Opus design pass.

## Round procedure

| Step | Rule | Reason |
|---|---|---|
| Round 1 | Broad review of the PR head against the merge base, requirements from the PR title and body | Same procedure as `/review-and-fix` |
| Checkout | Fresh full clone in a temporary directory, exact head SHA, review run with an allowlisted environment (`PATH`, locale, proxy and certificate variables, the Codex home for its auth, or for a Claude reviewer on a declared pull request the OAuth token or a copy of the real `.credentials.json`; see the Reviewer row) and an empty `HOME` otherwise. The runner itself runs with that empty `HOME`, so `approve.js` hands the engine the account's real home (`reviewRealHome`) and the real `CLAUDE_CONFIG_DIR` (`reviewDenyRead`). The Codex profile denies every entry of the real home except the way to the checkout, the review's own directories and the Codex binary, so the account's credential files (gh, ssh, cloud, Claude, Codex) are not readable by absolute path. The Claude reviewer has no such restriction | The checkout is untrusted, and a prompt injection could otherwise read a credential file and quote it in a published finding. Checked with a decoy file in the real home: readable to `codex exec` under the old profile, refused under the new one, with `git` and writes into the checkout still working. Entries created in the home after a Codex review starts are not denied |
| Submodules | Each gitlink the pull request changes is checked out at its own path in the review clone, in a fresh `.git` made with `--template=` (no hooks or configuration from the pull request), and `diff.submodule=diff` is set, so the engine's diff holds the submodule's own hunks. `.gitmodules` is read as a git blob; only a GitHub repository qualifies (`https://github.com/O/R`, `git@github.com:O/R`, `ssh://git@github.com/O/R`, `../R`, `../../O/R`), and the fetch url is built from `O/R` by `approve.js`, never taken from `.gitmodules`; `git submodule` is never run. The submodule must be readable by the account and public, or the pull request repository itself (compared by the name GitHub resolves). One level only. A range that fails any of this is recorded on the round as `unreviewed` with the reason `url`, `path`, `unreadable`, `audience`, `fetch` or `nested` (a submodule the pull request adds is checked for nested submodules too); the review says so, is a `COMMENT`, and no approval is posted for that head. The next round reviews the whole pull request again and retries. A removed submodule needs nothing fetched. A finding below a gitlink is verified in the submodule checkout and is posted in the review body, never inline | A gitlink diff is only `Subproject commit` lines, so the reviewer could not judge the change. A `.gitmodules` url is attacker-chosen (`file://`, `ext::`, an option-shaped string), so none of it reaches git. A private submodule would otherwise be quoted into a review its readers may not be allowed to see; collaborators are per repository, so same owner does not mean same readers. The submodule `.git` is writable by an unconfined reviewer, the same exposure the clone's `.git` already has |
| Reviewer | The reviewer is the harness's own (`claude` under Claude Code, with `CLAUDECODE` set, `codex` otherwise). `start` never falls back to the other vendor: when the harness's own reviewer cannot run it exits non-zero with one line saying why, writes no ledger, and names the other reviewer as an option the user may choose. `--reviewer <other>` or a resumed ledger is kept and refused the same way when not ready; `SKILL.md` has the model pass `--reviewer <other>` only when the user asked for the other vendor in their own words. `codex` is ready when it is installed and logged in (`auth.json` in the Codex home) and is confined. `claude` is not confined (#366), so it is ready only on a pull request with a trust declaration in its ledger (see Trust); under Claude Code it then needs nothing else, because it runs as the session's own subagents (see Subagent transport); elsewhere it also needs the `claude` binary and a login (`CLAUDE_CODE_OAUTH_TOKEN`, or a `.credentials.json` in the Claude configuration directory). Without a declaration `start` under Claude Code refuses with `it cannot be confined yet (#366), so <repo>#<pr> is reviewed by it only after you declare that you trust its author; or ask explicitly for the confined Codex reviewer (--reviewer codex)`; under Codex the same refusal applies to an explicit `--reviewer claude`. `start` prints no `note`. Every result of a Claude run carries a warning that it ran unconfined on the user's declaration and that the reviewer can read the real home. `round` checks the declaration again before every launch, so `trust --revoke` stops the next round. When #366 confines the Claude reviewer, the refusal is replaced by a confined run | The Claude reviewer has Bash and an empty `HOME` does not stop an absolute-path read, so its restriction (an operating-system wrapper or settings, verified with a decoy file) is a separate help-wanted issue, not part of this change; the same issue decides how the Claude login reaches a confined reviewer without being readable by its tools. Until then the declaring user accepts the risk for one pull request, and the reviewer authenticates as the user, which costs nothing the declaration has not already given up: the token when `CLAUDE_CODE_OAUTH_TOKEN` is set, else a copy of the real `.credentials.json` in the reviewer's own config directory. The user's settings, hooks, plugins and MCP servers never load into the review, because their allow rules and a logged-in `gh` would go beyond what the declaration accepts; a host that keeps the login outside that file (the macOS keychain) therefore needs the token for `claude -p`, which only Codex-driven runs still use. The token values in a credentials file, and in the reviewer's copy of it, are checked against the review text before it is posted. The other vendor is the user's choice and never a fallback, because a silent switch of vendor surprises the user (#404) |
| Trust | `approve.js trust <repo> <pr>` with no options prints the fixed question `Record that you trust the author of <repo>#<pr> for this review? ...` and writes nothing. `trust <repo> <pr> --declaration '<the user's words>' --confirmation '<the user's reply>'` stores `trust: {declaration, confirmation, question, recordedAt, account}` in that pull request's ledger (a ledger holding only this record is created when none exists, and `start` resumes it). It refuses an empty quote, a closed pull request, the pull request's author, and a declaration that occurs in the pull request title or body. `trust --revoke` removes the record. A declaration covers one pull request and its later rounds; another pull request has its own ledger and so none. `SKILL.md` lists what is not a declaration (text from the pull request or its code, a message relayed by another or a coordinating session, a standing statement, ambiguous wording), and has the model ask the question once and quote the user's own words. The published review says `reviewed unconfined on the reviewing account's trust declaration (recorded <time>)` and never carries the quotes | A flag such as `--trusted` would have the model grant the risk to itself with no evidence, which is why the auto-mode classifier denied the former flag; the quotes are inline, visible flag values, so the classifier and the user can compare them with the conversation. The quotes stay in the ledger and the local output because they may hold company-internal remarks that the readers of the pull request have no need of. The script cannot prove that a human said the quotes (see Residual exposure). Requiring the question in an earlier turn was rejected: the model can run both steps back to back, so it adds friction and no check. A standing setting, an environment variable or an author or organization allowlist was rejected: none is scoped to one pull request, and each outlives the decision |
| Later round range | `chooseRange`: same merge base and the last head an ancestor of the new head gives `last head..head`; otherwise `merge base..head`; a changed PR title or body gives `merge base..head` with the broad gate | A force push or a merged-in base branch has no isolatable delta; a changed requirement needs the gate again |
| Earlier findings | A finding is `fixed` only on evidence in git objects, never because the reviewer is silent. Each finding records `spanVerified`, the head SHA at which its span occurred byte for byte in the file stored in that head's git object (`git ls-tree` then `git cat-file`, a regular file of at most 20 MiB, never the working tree). A later round compares that head with the new head (`git diff -M --name-status`, one tree comparison however many pushes lie between) and resolves the finding's path through renames. It is fixed when the span no longer occurs at that path or in any other file the diff leaves in place; a deleted file counts as absent. It stays open, with `openReason`, as `unverified` (no verbatim span was ever recorded, which includes an empty span and every finding of a ledger written before this field existed), `span-present` (the span occurs at the path or moved to another file, and the finding follows it), `raised` (the reviewer raised it again) or `path-unresolved` (the old head cannot be fetched, or the path is a symlink or file over 20 MiB at the new head, or below a gitlink whose checkout is missing). `unverified` and `path-unresolved` findings cannot be settled from the code: the `round` output lists the blocking ones as `held` and says `waive` or `reclass` to minor clears them. Open findings are still passed to the reviewer (with the path after a rename) so it can raise one again under the same id, which keeps it open and not posted again; telling it decides nothing. `approve.js` passes them as the runner option `priorFindings` (`id`, `file`, `summary`), separate from `reviewerGuidance`, which stays the user's `::` text for every role. `round-plan.js` `priorFindingsClause` gives `correctness` and each `gate` panel lens only the findings (up to 20 each) whose id starts with a prefix `allowedFindingPrefixes` accepts for that role, so a reviewer is never told to write an id its artifact rejects, and no id is renamed for it | The reviewer's silence is a signal a prompt-injected reviewer controls, and the checkout is writable by the reviewer inside the Codex sandbox, so neither can fix a finding. A push that changes only a file mode shows `M` in name-status and the reviewer only a mode line; the span is still there, so the finding stays open. Matching is exact bytes with no whitespace or line-ending normalization, so a span the engine reflowed does not verify and is waived. A fixed finding the reviewer raises again with the span verbatim at the head reopens in place, and a re-raise of an unverified finding with the span verbatim verifies it; a re-raise matching only by id never replaces a span |
| Publication | One review per round, `commit_id` set to the reviewed head, event `COMMENT`, or `APPROVE` when the round is clean. Never `REQUEST_CHANGES` | The clean round's review is the approval |
| Published finding | Key is the hash of the file and the whitespace-collapsed span, or file plus id when the span is empty. A finding already in the ledger is listed as "Still open", not posted again | A span survives an id the model renamed |
| Fixed finding | The next review body carries one line, "Fixed since `<sha>`: ids" | Replying to or resolving another account's threads is out of scope for the first layer |
| First line | `<!-- concord-approve: <head> round:<n> base:<range base> -->` | `services/pr-review/scan.sh` treats a first line starting with `<!-- concord-review` as scheduling evidence, so the skill uses a different prefix |

## Finding locations

Finding-producing reviewer prompts require continuous verbatim source snippets, preserving whitespace and line breaks. Explanatory ellipses and pseudocode are not source anchors. Omissions use a related existing statement in the named file as their anchor.

The skill enables one optional anchor extraction call after the verified review result, through the same provider launch, sandbox, cancellation and protected-artifact boundary. It requests locations for at most 20 findings whose spans do not occur in their committed source. Only regular UTF-8 git blobs up to 1 MiB in the top-level reviewed commit are eligible; findings inside submodules retain their body-only publication and are not re-anchored from checkout contents. The extractor reads the named source and returns an index and a snippet, without changing the finding's identity, file, category, summary or requirement. The runner accepts a correction only when its nonempty snippet is at most 8192 UTF-8 bytes and occurs exactly once in that same committed file. It derives a single-line anchor's line from those bytes. A multiline anchor keeps a null line so the publisher can select the first line of the span overlapping a diff hunk, even when its leading context starts outside the hunk. The original reviewer artifacts remain sealed; the extraction has its own round artifact.

Existing verbatim spans and their engine line numbers remain unchanged. A malformed response, missing or ambiguous correction, unreadable source, or failed extraction preserves the original finding. There is no second extraction attempt and no fuzzy location matching. Checkout or artifact tampering, cancellation and launch-budget denial still stop the run. A line comment requires the resulting line to be inside a diff hunk; a finding in a file the diff names but outside every hunk is a file comment, and a finding in any other file stays in the review body. A finding whose anchor remains unverified keeps the existing `held` and waiver behavior.

## Subagent transport

Under Claude Code, `claude` reviews through the driving session's own subagents instead of a `claude -p` process, so the session's login is used and no token or credentials copy is needed on any platform (#375). The transport is chosen on every call from `CLAUDECODE` and is not stored in the ledger; the ledger records `claude` as before, and a ledger written under Codex continues as subagents under Claude Code. `claude -p` remains for Codex-driven runs, where it still needs a login or `CLAUDE_CODE_OAUTH_TOKEN`; that is what is left of #375. Without the user's setting nothing changes: the confined Codex reviewer runs, and `round` on a `claude` ledger is refused.

| Decision | Rule | Reason |
|---|---|---|
| Hand-off | `round` stays a single process and asks the session for each role. The runner's `spawn` becomes `scripts/broker.js`: it writes the role's prompt to `prompt-<id>.md` and `request.json` in the round's temporary directory and waits for `done-<id>`. The session starts `round` in the background and loops on `approve.js next [--done <id>]`, which prints `subagent-request` (id, role, prompt file, model), `waiting` after 540 seconds, or `finished` when no round is registered. The round registers after its first GitHub calls, so the session trusts `finished` only once the background `round` has exited, and otherwise calls `next` again. `next` takes no lock; the round's pid and directory are in `<ledger>.run.json`, written before the clone starts and removed when the round process exits | The script cannot call the Agent tool, and only the session can. A live process keeps the runner's in-memory seals (`protectedReviewFiles`, `trackedBefore`), the ledger lock, the single reviewOnly telemetry write and the engine snapshot as they are, so the checks that run after a `claude -p` launch run unchanged. Stopping the round after each request and resuming it was rejected: it forgets the seals between calls, so a subagent's rewrite of a sealed artifact would go unnoticed, its second telemetry write fails, and the lock is free between calls. Having the session run `review-cli` verbs itself, as `/review-and-fix` does, was rejected because the sealing, repair and anchor checks would become prose the session follows |
| Requests | One open request at a time, in the order the runner runs the roles: intent, correctness, gate, verify, gate-verify, then the anchor extraction. Ids count up; `--done` is accepted only for the open id, so a retried role (the correctness coverage retry) gets a new id | Same ordering and same prompts as the `claude -p` path; running correctness and gate together would change that order for a few minutes' gain |
| Prompt | The session passes the prompt file's path and no contents: "Read `<file>` and do exactly what it says. Reply only `done`." The file is the runner's prompt plus the path of the checkout (a `claude -p` process starts there; a subagent starts in the session's directory) and a note that no command can be run: judge by reading, and `blocked` is for a file that must be read and cannot, not for a command | The session cannot alter or summarize what the role is told. The role prompts ask to measure, run or execute and say to write `blocked` when that tool is missing; a subagent without a shell would otherwise fail the round for the tool, not for the code |
| Subagent | `plugins/concord/agents/pr-reviewer.md` with tools `Read, Grep, Glob, Write` and no shell or MCP tools. The model is `ledger.model` when set; `start` and `round` refuse any value but `sonnet`, `opus` or `haiku` under this transport | A plugin agent can fix its tool list; a general-purpose agent has a shell and every MCP tool of the session. The Agent tool takes only those model names |
| Artifacts | The subagent writes only the role's artifact file named in its prompt, the same file as under `claude -p`. The runner reads it exactly as it reads a `claude -p` artifact: `artifact-normalize`, repair, seal, `checkReviewCheckout`, `checkProtected`. The prompt file's hash is checked when `done` is seen. The session writes nothing in the round's directory except through `next` | Nothing a reviewer may write differs between the transports |
| Failure | A role whose artifact is missing or malformed fails the round as under `claude -p`: non-zero exit, nothing posted, ledger unchanged, temporary directory and run file removed, no retry. A non-empty `blocked`, a modified tracked file, a moved `HEAD` and a changed sealed artifact fail it the way they do today. The wait for one request ends after one hour with `no subagent answered the <role> request in time`. A head that moved during the review is found after the review and discards the round as today | The failure rules are the ones the runner already applies; the new case is only a session that never answers |
| Stop | TaskStop on the background `round`, then `stop` as before. A killed `round` cannot clean up (it waits in `spawnSync`), so the runner it started checks for its parent on every poll, and when the parent is gone it removes the attempt's directory and ends. The stale run file names a pid that is gone, which `next` reads as no round | The ledger lock is reclaimed from the dead pid by the next call; the runner and the clone do not outlive the round |
| Credentials | No copy of the Claude login is made, and `claude` need not be installed. The check on the review text still covers `GH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `OPENAI_API_KEY`, `gh auth token` and every long string of the real `.credentials.json` | Publication, ledger, span verification and approval run after the review comes back, in the same process, so they are the code that runs for `claude -p` |

## Review language and effort

`start --language <tag>` and `start --effort <level>` are ledger fields like `--model`: set at `start`, replaced by a later `start` that names them, kept by one that does not, and read by every `round`.

| Decision | Rule | Reason |
|---|---|---|
| Language scope | The reviewers write each finding's `summary` and `requirement` in the language. The review header, the "Fixed since" and "Still open" lines, the finding count lines, the category label and the first-line marker stay English. `id`, `file`, `span`, `category` and code identifiers are never translated | The finding text is what the reader needs in their language. A translated phrase table per language in `publish.js` is a layer to maintain for boilerplate, and the marker is parsed by scripts |
| Language carrier | The runner option `reviewLanguage` becomes a clause after the span clause in the prompts of the roles that write findings (`correctness`, `verify`, `intent`, `gate`, `gate-verify`), asking for the BCP 47 tag. It is not part of `reviewerGuidance` | Guidance is "priority hints only" and is rebuilt each round from the open findings; the language changes the output format and must hold in every round and role |
| Language value | A BCP 47 tag (`ko`, `en`, `zh-TW`), checked by `^[a-z]{2,3}(-[A-Za-z0-9]{2,8})*$`; a language name is refused, and `SKILL.md` has the model convert the user's words | One accepted form means the prompt clause and the ledger agree |
| Spans | The clause says to copy `span` exactly. A translated span does not occur in the file, so the existing byte-for-byte check leaves the finding `unverified`, held and blocking approval | The check already fails safe; a second one would repeat it |
| Effort levels | Codex: `low`, `medium`, `high`, `xhigh`, passed by the runner as `model_reasoning_effort`. Claude: those and `max`, passed as `--effort` to `claude -p` and as `effort` in the subagent request, which `SKILL.md` has the session pass as the Agent tool's `effort` parameter | Each path uses its own control. The Agent tool takes `effort` only when the user asked for it, and the user did, at `start` |
| Unusable effort | `start` refuses a level the chosen reviewer does not take (`max` with Codex) and writes nothing | The reviewer is known at `start`; a level dropped later would run a review the user did not ask for |
| Natural language | `SKILL.md` maps the user's words ("한글로" to `ko`, "opus high" to `--model opus --effort high`) and has the model set an option only on an explicit request, ask one question when the request conflicts or is unclear, and never edit plugin files; when an option is missing or refused it tells the user | An installed copy edited to add an instruction ran two review rounds on modified code (#390) |

`start` prints the stored `model`, `language` and `effort`, so the user sees what the rounds will use.

## Approval condition

`evaluateApproval` approves exactly when all of these hold: the reviewed head is the live head, the pull request is open and not a draft, the reviewing account is not the author, no approval was already given for this head, and no finding in the ledger is open with class `blocker`. A finding without class `minor` is a blocker. An open minor does not block; the approving review lists it as a follow-up. A blocker is cleared by a fix, by `waive`, or by `reclass` to minor. A waived finding is recorded in the ledger and does not block. A blocker the code cannot settle (`unverified`, `path-unresolved`) is cleared only by `waive` or `reclass`, by finding id or, when several open findings share an id, by key; an unsettled minor needs neither.

## Finding class

| Decision | Rule | Reason |
|---|---|---|
| Source | In review-only runs the engine asks the correctness and verify roles for `releaseBlocking` and `rationale` with the clause the gate roles already carry (`classify` in `round-plan.js`, set by the runner when `reviewOnly`). The `findings` verb reports `class`: `minor` exactly when `releaseBlocking` is an empty array, `rationale` is non-blank and gate-verify gave no `blockingReason` (`gateFollowUpEligible`), otherwise `blocker`; it also reports `releaseBlocking` and `rationale`. Intent findings carry no class and are blockers. `review-and-fix` prompts are unchanged | One definition of minor for the whole plugin, with the same categories as the gate findings and the same fail-closed reading of a missing or malformed field. A separate classifier in the skill would be a second model call outside the runner's confinement, judging from the summary without the reviewer's evidence |
| Ledger | A finding stores `class`, `reason` (the collapsed rationale, `unclassified` when there is none) and `releaseBlocking`. `lib.classOf` accepts `minor` only for an empty `releaseBlocking` and a rationale, so a runner that says less blocks. The class is set when the finding enters the ledger and is not changed by a re-raise, a reopen or a later verification; of several raised findings with one key the blocker wins. A ledger entry without `class` is a blocker | A reviewer that reclassifies a known finding each round would make approval flip; only the user changes a class |
| `reclass` | `reclass <repo> <pr> <id\|key> <blocker\|minor> --reason '<line>'` on an open finding, both directions, reason required. It sets `class` and `reason` and appends `{from, to, reason, at, account}` to `reclassed`. A change to minor approves as `waive` does; a change to blocker posts nothing and the output says an earlier approval stays on GitHub. The script cannot know who typed it (see Trust) | A reviewer can under-classify, so the user must be able to raise a minor as well as lower a blocker |
| Publication | Each finding is labeled `(blocker: <categories>)` or `(minor)` with its reason, and the count line says how many block. An approving review says no blocking finding is open and lists every open minor, inline ones included, under `Follow-ups (not blocking)` with file, summary, reason and id. `Still open` marks minors | The body is the complete follow-up list for the person who merges |
| Comment placement | A finding whose line is in a diff hunk is a line comment. A finding whose file is in the diff but whose line is in no hunk (or has none) is a file comment, whose text starts with `Line <n>:` when the engine gave a line. A finding in a file the diff does not contain stays in the body. The review is built as a pending review: a REST `POST .../reviews` with the marker line as body and no event, one GraphQL `addPullRequestReviewThread` per comment (`subjectType` `LINE` or `FILE`), then `POST .../reviews/<id>/events` with the final body. A thread GitHub refuses is listed in the body in place of its comment; the other comments stay. The head is checked again before the submission, and a moved head deletes the pending review. A pending review by this account whose body starts with the marker is deleted at the start of the next publication; one without the marker is the reviewer's own draft, so the round fails and leaves it | The REST review call has no file-level comment and rejects every comment when one is bad; only a thread added to a pending review can be file-level and fail alone. Nothing is visible before the submission, so an `APPROVE` is posted only after every comment has settled. The review keeps its REST id and `commit_id`, so the ledger, `landed` and the recovery of an unsettled `APPROVE` are unchanged. Retrying a refused line comment as a file comment was left out: a line GitHub refused is rare once the hunks are known. Any failure of a thread call (a timeout after GitHub accepted it included) counts as a refusal, so such a finding can appear both as a comment and in the body; the duplicate loses no finding |
| Waive | Unchanged: it dismisses a finding of either class, and a waived minor leaves the follow-up list | |

Required checks are not part of the condition. Approval is a code-review verdict; merge gating belongs to branch protection. A draft is never approved: the skill tells the user, and invoking it again after the pull request is ready approves the unchanged head without a new round.

## Wait

`scripts/watch.js` reads the ledger without writing it, polls `gh` every 60 seconds, prints one JSON event line, and exits. It runs under `mien exec <profile> --` where the reviewing account is not the ambient one.

| Harness | How the session waits | Model cost |
|---|---|---|
| Claude Code | `watch.js --max-wait 6600` as a Bash `run_in_background` command with `timeout: 7200000`, which wakes the session when it exits; on `idle` or a killed run the session runs the same command again | one small model call per window, about 13 a day; the 7-day wait is about 92 windows |
| Codex | `watch.js --max-wait <seconds>` in the foreground; after that many seconds without an event it prints `{"event":"idle"}`, and the session runs it again | about one small model call per window; a window is bounded by the shell tool's command timeout (540 seconds by default in the skill) |

Monitor is not used on Claude Code: it stops after 30 minutes, while a background Bash command runs up to 7200 seconds. The explicit 7200000 ms timeout replaces the 30-minute background default, and 6600 leaves 10 minutes for a poll, `gh` latency and startup, so `idle` is printed before the host kills the command; a killed run is treated like `idle` and a non-zero exit with no JSON line is reported, so a crash is not re-armed in a loop. The session re-runs the identical command it built once with absolute paths and never edits, wraps or replaces `watch.js`. A user stop calls TaskStop on the recorded task id. Codex has no background process that wakes a conversation, so its wait costs the same per window but windows are 540 seconds; the skill tells the user after six idle windows in a row. `<ledger>.watch.json` carries the head seen, the nudge shown and the failed polls in a row from one run to the next, so a new window does not restart the two-poll head stability check, repeat a nudge or hide an outage behind `idle`. A window ends at its deadline: the sleep between polls is cut to the time left. The ledger stays the session's and `approve.js`'s alone.

| Event | Fires when |
|---|---|
| `round` | The head differs from the last reviewed head and the author replied after the last review, and the head was the same on two consecutive polls. After a failed round (`attempt` in the ledger) the head must also differ from the attempted head, or a reply must be newer than the failure |
| `merged`, `closed` | The pull request reached that state |
| `nudge` | Only a push, or only a reply, has arrived and 24 hours have passed since the last review. It repeats only for a new head or reply, and posts nothing; the session tells the user |
| `timeout` | 7 days since the last review |
| `idle` | Only with `--max-wait`: the window ended without an event (exit status 0); the session runs the same command again |
| `error` | Ten consecutive failed polls, counted across bounded runs (exit status 1) |

A round that fails after the head snapshot (the runner exits non-zero, its result is not a review, a credential is found in the review text, or the post fails) is recorded in the ledger as `attempt` (`head`, `at`) by `approve.js`, the only writer of the ledger; the watch compares against it and still never writes. The ledger is the one record every process and every machine reads, while `.watch.json` belongs to one watch run. The session reports the failure to the user and restarts the watch: it neither retries the round nor stops for good.

A reply is a comment by the pull request author after the last review, either in a thread of a review the skill published (`in_reply_to_id` is one of its comment ids) or on the pull request conversation, which is the only way to answer a finding posted in a review body. Who pushed does not matter. A push or reply alone, a CI change, a label, or a comment by anyone but the author wakes nothing. A user stop ends the watch and is recorded in the ledger. At most 10 rounds run per pull request, and nothing is posted on any stop.

## State

One JSON file per repository, pull request and reviewing account at `${REVIEW_APPROVE_STATE_DIR:-${CLAUDE_CONFIG_DIR:-~/.claude}/concord/review-until-approve}/<owner>__<repo>__<pr>__<login>.json`, outside any checkout, written atomically, locked by process id so a second session on the same pull request is refused. It holds the reviewing account, the author, `rounds[]` (head, range base, merge base, requirement hash, submission time, review id, comment ids), `findings[]` (key, id, category, file, span, `spanVerified`, summary, status `open|fixed|waived`, `openReason`), `nudged`, `approval`, `stopped`, and `pending` (the head, the newest review id before the post, the round about to be recorded and the findings it would leave, written alone before an `APPROVE` is posted and removed once the review is recorded; the ledger's own findings change only when the review is recorded). What happened since the last review is derived from GitHub on every poll, never stored. Invoking the skill again on a pull request with a ledger resumes it: a moved head runs a round at once, since the invocation is the user's request; otherwise the watch restarts.

## Identity

Every `gh` call, read and write, runs as the account the user names (`mien exec <profile> -- gh`, else the ambient account), recorded as the reviewer. A different account has its own ledger (the login is in the file name) and starts at round 1. If the account is the pull request author, the skill refuses before round 1, because GitHub rejects self-approval. Approval is `POST repos/{o}/{r}/pulls/{n}/reviews` with `event=APPROVE` and `commit_id`, because `gh pr review --approve` cannot pin the commit and races with a push. A push between the last head check and the POST is accepted: the approval is pinned to the reviewed `commit_id`, so GitHub shows it against that commit and branch protection decides whether a later push dismisses it. An account below write permission is warned that its approval will not satisfy branch protection.

## Unattended deployment

The loop can later run unattended, with GitHub Actions or `services/pr-review` reacting to the push and the reply instead of a session's shell loop. The pure decisions (`chooseRange`, `isPublished`, `classifyPrior`, `evaluateApproval`, `repliesSince`, `wakeDecision`) are in `scripts/lib.js`, and the publication code is separate from the watch. Neither depends on Monitor or a live session. No unattended variant is built.

## Residual exposure

- A failure before the head snapshot (gh unreachable) and a round killed hard (SIGKILL, power loss) record no `attempt`, and the watch wakes again at once on the same head.
- A finding whose id has a prefix that no reviewer role accepts reaches no reviewer. No such prefix exists.
- Prior findings are kept in the approval ledger, not in the review-cli run ledger, so a run archived by review-cli does not show them.
- If the `APPROVE` post errors and the head then moves, the pending marker is not settled against GitHub's review list until a later `start`, `round`, `approve` or `waive` reads it; an approval GitHub accepted for the old head stays recorded only on GitHub until then.
- A body-mode retry after a timed-out post can post a second review when GitHub's review list lags behind the first.
- Fixed means the quoted text no longer occurs, not that the defect is gone; a trivial edit inside the span fixes the finding, and the next diff review is what catches a defect that remains. A fix that is later undone is noticed only when the reviewer raises the finding again. A reformat that changes the quoted bytes (re-indent, CRLF) fixes the finding for the same reason.
- A finding for which bounded extraction cannot establish a verbatim span stays unverified and, as a blocker, is cleared only by `waive` or `reclass` to minor. A reviewer that withholds a finding at round 1 is not detectable.
- The review-only state directory is writable by the reviewer (it is the artifact channel); the runner pins and hashes the files it later trusts, so a later role cannot change them unnoticed, but the directory is not read-only.
- The Claude reviewer is not confined (it runs only on a pull request with a trust declaration in its ledger) and is not trusted to leave the review clone intact beyond the `GIT_NO_REPLACE_OBJECTS` setting; the confinement is tracked in issue #366.
- The script cannot tell who typed a trust declaration. A model steered by a prompt injection could invent both quotes; the refusal of a declaration that occurs in the pull request text, the visible inline quotes the auto-mode classifier can compare with the conversation, and the ledger record expose this after the fact and do not prevent it.
- The subagent transport is not as narrow as the `claude -p` reviewer in two ways. The subagent's reply goes into the driving session's context, which `claude -p` output never did; `SKILL.md` tells the session to ignore it and the agent to answer `done`, and a prompt-injected pull request that gets through is a prompt injection of the session. The subagent runs under the session's permission mode and allow rules and the user's hooks fire on its tool calls; without a shell and MCP tools it cannot run commands or reach connectors, but its `Write` can reach any path that mode allows, and the macOS Keychain login is not among the strings checked in the review text (no shell means no `security` command to read it). Confinement is #366.
- Whether `Read` and `Write` on the round's temporary directory, which is outside the project, raise a permission prompt for every request, or are denied in auto mode, has not been measured. If they do, the session reports the denial and the round fails at the missing artifact.
- A second session can call `next` and answer a request that the first session also answers; the second `--done` for the same id is refused, but both may have spawned a subagent that wrote the same artifact.
- A run file left by a round killed with SIGKILL names a pid; if the system reuses that pid for another process before the next call, `next` reports a running round whose broker directory is gone, and the session sees `waiting` until it stops. The next `round` overwrites the file.
