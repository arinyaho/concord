The review CLI is invoked as `node "<review-cli>" <verb> ...`, where `<review-cli>` is the harness-resolved path to the review CLI script (each packaging layer wires this to its own copy of the script). It is the deterministic authority on rounds, dedupe, and termination; you drive it and spawn the review/fix subagents, but you make NO judgement about findings, DoD, or when to stop -- the CLI decides.

Concord IS the reviewer. The findings for every round come from the review subagents YOU spawn against the diff (steps 2-3) -- never from a bot, CI check, or human review posted on the PR. Do NOT `gh pr ready` and wait, do NOT poll or `ScheduleWakeup` for a Codex/Copilot/CI review to land, and do NOT treat any external review as this loop's rounds or gate. If the target happens to be a PR that also gets bot reviews, ignore them here; they are not your input and waiting on them is the failure this loop exists to replace. Once `round-start` says `work`, the very next thing you do is dispatch this round's review subagents in THIS session.

Arguments: `<arguments>` -- the harness-resolved invocation arguments; each packaging layer wires this to its own argument-substitution token (the same way `<review-cli>` is wired to the CLI path).

Determine the target ref: empty -> current branch (`git branch --show-current`); `resume <ref>` -> the ref after `resume`; else the arguments as-is. Optional base ref is the second token (default the repo's remote main branch, `origin/<main>` -- a local base can be stale (behind its remote), which sweeps unrelated merged changes into the diff).

To review a local file or document instead of a git diff (a design/spec `.md`, a note -- reviewable even in a directory that is not a git repository), pass a single `file:<path-or-glob>` token as the ref, where `<path-or-glob>` is a literal path OR a simple single-`*` glob resolved against the repo root: `round-start file:note.md` or `round-start file:*.md` (the glob pulls in every match, concatenated in sorted order). This is the ONLY file-target form -- there is no `--files` flag. A file target has no base and no DoD; `round-start` reports `targetType: 'file'` and the per-round flow branches on it (see step 2).

Broad review is ON by default and needs no flag: the CLI fires the gate pair on the first round only, so it costs two subagents once per run, not per round. Pass nothing. The one case that needs a flag is an explicit opt-out -- if the arguments contain the literal token `--no-broad`, or the user asked for a diff-local-only/fast review in their own words, pass `--no-broad` to every `round-start` call for the rest of this run (harmless to repeat -- the opt-out is sticky). `--broad`/`--gate` remain accepted and re-arm a run that opted out earlier; do not add them on your own initiative, they change nothing on a default git run. One exception where they do change something: a `file:` target is broad-disarmed by default (the gate pair's prompt is written against a git diff and sweeps the repository, which a doc review does not need), so pass `--broad` only if the user explicitly wants the tree swept against that document.

Also check whether this invocation asked to run without an executable DoD gate: if the arguments contain the literal token `--no-dod`, pass `--no-dod` to every `round-start` call for the rest of this run (harmless to repeat -- the deferral is sticky once applied). The review gates still run; the executable DoD is reported as deferred and never faked to a pass. Pass this flag ONLY when the user's invocation asked for it. Never add `--no-dod` on your own initiative to get past a failing gate -- skipping a check that is failing is the user's decision, never yours. (You do not need it for a repo with no `review.config.json`: that case already defers on its own.)

**Append this clause verbatim to EVERY review-class subagent prompt you spawn** -- correctness, verify, intent, gate-review, gate-verify, each panel lens, each adversarial verify. The loop makes reviewers hunt verifier-gaming in the diff; this is the same guard pointed at the reviewer's own evidence, and nothing else in the loop provides it:

> If you were told to establish something by a specific method -- measure it, run it, execute the check -- and you cannot run that tool (missing, denied by permissions or sandbox, crashed, timed out), do NOT quietly substitute a weaker method and do NOT stay silent. Add `"blocked": ["<tool>: <what failed>"]` to your artifact and stop there -- keep `"status":"ok"` and leave the arrays empty; `blocked` is what fails the round, there is no `"status":"blocked"`. That fails the round loudly, which is the correct outcome; a schema-valid verdict from a check you never actually ran is indistinguishable from a real one and is worse than a failure.

Never soften that clause, and never accept an artifact from a reviewer you know was blocked -- a non-empty `blocked` is terminal wherever the CLI reads the artifact (`artifact-normalize` for the fail-closed roles, and `plan-fixes`/`gate-panel-round-record` for the leniently-read gate-verify and panel artifacts), precisely so a degraded reviewer cannot produce a verdict.

Run this loop. Do each step in order; do not skip, reorder, or improvise termination.

1. `node "<review-cli>" round-start <ref> [base] [--no-broad] [--no-dod]`
   - `decision: "terminal"` or `"no-op"` -> stop; report the CLI's message.
   - `decision: "work"` -> continue: proceed straight to step 2 in THIS session. Do not pause, defer, or wait on anything external first. Note the `round` number `n`, the `stateDir` path it prints (`stateDir` is the CLI-owned directory for this run's artifacts; every path below is relative to it), and the `dodPassed` and `dodDeferred` booleans -- step 2 passes them to the correctness subagent. When `dodDeferred` is `true`, `dodPassed` is `true` only because nothing blocked the round, NOT because a gate ran and passed; the two must never be conflated.
2. Read the file at `<stateDir>/round-<n>-diff.txt` (the file round-start just wrote -- for a git target this is a diff; for a file target this is the current content of the target file). Spawn ONE correctness review subagent per the harness spawn-include (clean context -- do not paste your own prior reasoning). The prompt to give it depends on `targetType` from the round-start output:

   **If `round-start` reported `targetType: 'file'` (doc review):** Use this DOC-REVIEW prompt instead of the code-correctness prompt below. Note that a file target has no DoD step (round-start reported `dodPassed: true` as a no-op) and fixes are plain file edits by the caller -- `commit-fix` is skipped for file targets, so skip step 5's `commit-fix` call.

   > Review the document at `<stateDir>/round-<n>-diff.txt` (the current content of the target file, not a diff). Find: internal contradictions, claims made without supporting evidence or reference, placeholders/TBDs/TODOs, over-claims (asserting something is proven/complete when the text does not establish it), and buried or omitted limitations. You are also handed the prior round's still-open findings -- for the SAME objection, REUSE its `id` verbatim so it dedups; only mint a new `id` for a genuinely new objection. Write ONLY to `<stateDir>/round-<n>-correctness.json`: `{ "status":"ok", "examined":["<file>"], "findings":[ {"id":"docreview:<stable-slug>","gate":"correctness","file":"<path>","span":"<exact offending text>","summary":"<one sentence>"} ] }` -- empty findings if nothing.

   **If `round-start` reported `targetType: 'git'` (code review, default):** Instruct the subagent to review the diff for correctness bugs, reuse/simplification/efficiency, AND verifier-gaming (hardcoded literals matching test inputs, weakened/deleted assertions, output emitted before the check runs, whether a fix explains WHY a test passes not just that it does). Tell it round-start's `dodPassed` result: if `true`, instruct it NOT to re-verify build/tests itself -- no sourcing a standalone typechecker, no A/B pre/post-diff rebuilds, no full test-suite reruns; trust that DoD already passed and spend its budget on logic bugs, reuse, and verifier-gaming instead. A single run of the repo's own already-configured build/typecheck command is fine if it genuinely needs one, but assembling tooling that doesn't already exist in the repo is out of scope. If `round-start` reported `dodDeferred: true`, do NOT give it the "DoD already passed" instruction at all -- tell it instead that no executable gate ran this run, and that a single run of the repo's own already-configured build/test command is acceptable if it genuinely needs one. If `dodPassed` is `false`, tell it DoD failed this round and that failure is tracked separately by the CLI -- it should still keep to the diff-and-surrounding-code review this step already asks for, not go root-causing the DoD failure itself. Ignore any intent-*.md file in the state directory; it is not part of your input. Review only the diff and the surrounding code. It MUST write ONLY to `<stateDir>/round-<n>-correctness.json` the JSON `{ "status":"ok", "examined":[<every changed file path it looked at>], "findings":[ {"id":"correctness:<stable-slug>","gate":"correctness","file":"<path>","span":"<exact offending text>","summary":"<one sentence>"} ] }` -- empty `findings` array if nothing. The `id` is a stable slug reused for the same bug across rounds.
3. Only after the correctness subagent from step 2 has finished and `<stateDir>/round-<n>-correctness.json` exists, spawn ONE verify subagent per the harness spawn-include (clean context) -- never in parallel with step 2, since it depends on that file; spawning it before correctness has written its output races an empty or missing file into a false "nothing to reject" result (the same "wait for the file" pattern as the gate-review -> gate-verify pair below, which races an empty or missing file into a silent no-op the same way). `plan-fixes`/`record` independently reject a verify artifact whose file predates its correctness artifact, as a harness-level backstop against exactly this race -- but that backstop only turns the failure into a loud one; it does not replace spawning them in the right order. It should re-review the candidate findings against the diff and write ONLY `{ "status":"ok", "rejected":[ {"id":"<id>","reason":"<one line naming what it actually ran, measured, or read to reject it>"} ] }` to `<stateDir>/round-<n>-verify.json` (the findings it judges false positives). The `reason` is mandatory and one line, not prose -- a rejection kills a confirmed finding, so it carries the same burden of proof the finding did; `artifact-normalize` retries a rejection that has none. Ignore any intent-*.md file in the state directory; it is not part of your input. Review only the diff and the surrounding code.

   If `round-start` reported `intentApplied: true`, ALSO spawn a separate intent-detector subagent per the harness spawn-include (in parallel with the correctness -> verify pair -- it doesn't depend on either's output). Its prompt is the following, with the blocked-tool clause above appended, and with round-start's `priorIntentIds` list pasted in verbatim where the prompt refers to it:

   > You are a design-conformance detector. Inputs: the diff at `<stateDir>/round-<n>-diff.txt` and the stated requirements at `<stateDir>/intent-<slug>.md`. Write a JSON file to `<stateDir>/round-<n>-intent.json` of the form `{ "status": "ok", "findings": [ ... ] }`.
   >
   > You are also handed `priorIntentIds` from `round-start` -- the still-open intent findings from the previous round. For the SAME objection against the SAME requirement, REUSE that `id` verbatim so the human re-reading the handoff recognises it as the objection they already saw; mint a new `id` ONLY for a genuinely new objection. Nothing dedupes intent findings by id, so a re-slugged repeat reads as a second, new problem.
   >
   > Raise a finding ONLY for an active contradiction of an explicit, stated requirement, on a line the diff added or changed: the intent states X unambiguously and a changed line does not-X. Each finding is `{ "id": "intent:<slug>", "file": "<changed file path>", "span": "<the exact contradicting changed line>", "requirement": "<the verbatim requirement text it contradicts>", "summary": "<one line>" }`. The `id` MUST start with `intent:`. The `file` MUST be one the diff changed.
   >
   > Do NOT raise: a requirement the diff is merely silent on (missing/incomplete); a contradiction on an unchanged file; "is this the right architecture / should this be refactored / does this match the spirit"; a requirement quoted from a non-normative part of the intent (a rejected alternative, background, an example of what not to do). If unsure whether something is an active contradiction or a matter of design taste, do not raise it. These findings are reported to a human, never auto-fixed.
   >
   > If there are no contradictions, write `{ "status": "ok", "findings": [] }`.

   If `round-start` reported `gateApplied: true` (normally round 1 only -- the CLI owns that decision; never spawn the pair on a round that did not report it, and never skip it on a round that did), ALSO run the gate pair alongside correctness/verify/intent -- as a unit, not each subagent independently parallel with those three. Within the pair the order is strict: spawn **gate-review** first and wait for it to finish writing `<stateDir>/round-<n>-gate.json`; only THEN spawn **gate-verify**, sequentially after -- never in parallel with gate-review -- because gate-verify's prompt reads that file as its input, and spawning it early races an empty or missing file into a silent no-op (the same "wait for the file" pattern as the correctness -> verify pair in step 3 above). Unlike the correctness gate, the gate subagents MAY Read and Grep the whole repository, and MUST consider the design/plan/AC -- read `intent-<slug>.md` in the state directory if it exists.

   **gate-review** (spawn per the harness spawn-include, clean context): "Review the diff at `<stateDir>/round-<n>-diff.txt` for defects a diff-local reviewer structurally cannot catch: design-conformance gaps, silent gaps (the design/plan/AC requires something the code omits), AC-coverage gaps, and cross-context violations (an unchanged file -- sibling or cross-repo -- whose invariant a changed line breaks). You MAY Read/Grep the repository and MUST read `<stateDir>/intent-<slug>.md` if present for the design/AC. Write ONLY `{ "status":"ok", "findings":[ {"id":"gate:<class>:<slug>","file":"<path, may be unchanged>","span":"<anchor>","requirement":"<the design/AC text it fails, if any>","summary":"<one sentence>"} ] }` to `<stateDir>/round-<n>-gate.json`. `<class>` is one of cross-context | silent-gap | ac-coverage | design-conformance. Empty findings if nothing. Report only; you never fix."

   **gate-verify** (spawn per the harness spawn-include, clean context, a DIFFERENT lens): "Re-review the candidate findings in `<stateDir>/round-<n>-gate.json` against the diff and the repository. Reject false positives and design-taste objections; keep only real, actionable gaps. You may also note a class of gap the first pass missed by adding it as a new `gate:` finding, in the same shape gate-review uses. Write ONLY `{ "status":"ok", "rejected":[ {"id":"<id>","reason":"<one line naming what you actually ran, measured, or read to reject it>"} ], "findings":[ {"id":"gate:<class>:<slug>","file":"<path, may be unchanged>","span":"<anchor>","requirement":"<the design/AC text it fails, if any>","summary":"<one sentence>"} ] }` to `<stateDir>/round-<n>-gate-verify.json` -- `rejected` is the false positives from the first pass (each with its one-line basis), `findings` is any NEW gap this pass caught (empty array if none)."

4. `node "<review-cli>" plan-fixes <ref>` -> `{ fixes: [{id, file, span, summary}, ...] }`.
5. For EACH fix in order (sequentially, one at a time -- never in parallel; two fixes may touch the same file): spawn a fix subagent that applies the minimal correct fix by editing the working tree, then writes ONLY `{ "status":"ok", "edited": true, "files": ["<path>", ...] }` to `<stateDir>/round-<n>-fix-<id>.json` (`edited:false` if it decided no change was warranted, in which case omit `files` or leave it empty). `files` MUST list EVERY file the fix subagent edited -- the finding's own file plus any companion edit it legitimately needed (e.g. a caller/import that had to change for the fix to be correct) -- so `commit-fix` commits the whole fix, not just the finding's file. Wait for it, then immediately run `node "<review-cli>" commit-fix <ref> <id>` -> `{committed, sha?, reason?}` BEFORE spawning the next fix subagent -- this commits only that one fix's declared files while they are the sole uncommitted change, so two fixes touching the same file land as two separate, correctly attributed commits.
6. `node "<review-cli>" record <ref>` -> `{ decision, handoff }`.
   - `decision.continue: true` -> go to step 1 for the next round.
   - If `record` returns `decision.intentReview`, print the handoff and stop: the run found changed lines that contradict stated requirements. These are reported, never auto-fixed. Resolve by editing the code (or correcting the design source) and re-running `/review-until-green <ref>`; the re-run re-fetches the intent and re-reviews. A finding you judge a false positive needs no command -- read it, and merge by hand if you choose (concord never merges anything itself).
   - If `record` returns `decision.gatePending`, print the handoff and stop: the diff-local loop is clean, but broad review has open advisory findings (design/AC/cross-context) for a human. These are never auto-fixed. Resolve by fixing the code or the design source and re-running `/review-until-green <ref>` (a fresh run re-evaluates broad review), or, for a finding you accept as out-of-scope/deferred, `review-cli.js dismiss <ref> <gateId>` so it stops surfacing. `gate-pending`, like a parked ledger, does not auto-clear -- re-run or dismiss.
   - If `record` returns `decision.panelPending`, the diff-local loop and broad review are both clean, but this repo has the holistic broad-review panel enabled (`gate.panel: true` in `review.config.json`) and it has not run yet this convergence attempt. Do NOT stop -- run the panel now, in THIS session, then call `record` again:
     a. `node "<review-cli>" gate-panel-round-start <ref>` -> `{ round: m, rejectedIds: [...], stateDir }`.
     b. Spawn 5 lens subagents in PARALLEL per the harness spawn-include (clean context each), one per class: `ac-coverage`, `design-conformance`, `cross-context`, `silent-gap`, `threat-model`. Each MAY Read/Grep the whole repository and MUST read `intent-<slug>.md` if present, same access as gate-review above. Tell each one the `rejectedIds` list from step (a) verbatim: "these were already raised and rejected in an earlier round without new evidence -- do not re-raise them unless you have found something the earlier round didn't." Each writes ONLY `{ "status":"ok", "findings":[ {"id":"gate:<lens>:<slug>","file":"<path, may be unchanged>","span":"<anchor>","requirement":"<the design/AC text it fails, if any>","summary":"<one sentence>"} ] }` to `<stateDir>/round-<n>-gate-panel-<m>-<lens>.json` -- `<lens>` MUST be the exact class name this subagent was assigned (`gate-panel-round-record` rejects a mismatch as a harness-failure). A missing or malformed lens file is treated as zero findings for that lens, not an error -- the round proceeds with whatever lenses did report. A lens that DECLARES `blocked` is the exception: that is the lens stating its check never ran, and `gate-panel-round-record` fails the round loudly rather than counting it as zero findings.
     c. Only after ALL 5 lens subagents from step (b) have finished -- never in parallel with them, since verify's input is their combined output, the same "wait for the file" pattern as correctness -> verify (step 3) and gate-review -> gate-verify above -- for EACH candidate finding they raised, spawn 3 independent adversarial-verify subagents per the harness spawn-include (clean context, prompted to REFUTE the finding, default to "refuted" if uncertain) and take the majority vote. Write ONLY `{ "status":"ok", "rejected":[ {"id":"<id>","reason":"<one line: the majority's basis>"} ] }` (the findings that did NOT get a majority "survives" vote) to `<stateDir>/round-<n>-gate-panel-<m>-verify.json`.
     d. `node "<review-cli>" gate-panel-round-record <ref>` -> `{ status: "running"|"done", round, dryStreak, newlyConfirmedCount, rejectedIds }`.
     e. If `status: "running"`, go back to (a) for the next panel round -- do not track round numbers or the rejected-ids list yourself, `gate-panel-round-start` reports both fresh each time. If `status: "done"` (2 consecutive rounds contributed nothing new), the panel has converged: call `record <ref>` again (back to the top of this step); it folds the panel's confirmed findings into the normal broad-review flow and returns a real terminal decision (`clean` or `gatePending`), never `panelPending` again for this convergence attempt.
   - Otherwise, `decision.continue: false` -> print the `handoff` verbatim and stop.

Never run more rounds than the CLI drives; the CLI enforces the round budget, the park-budget breaker, and convergence. A round is only real when its findings come from the subagents you spawned this session; if you ever find yourself reading a bot/CI/PR review to decide what to fix, or scheduling a wake-up to wait for one, you have left this loop -- stop and return to step 1. If a CLI verb exits non-zero with a `harness-failure:` message, stop and report it plainly -- do NOT characterize the run as clean or parked. A repo with no `review.config.json` is NOT one of those cases -- the run proceeds on the review gates alone and the handoff reports `DoD: DEFERRED`. Relay that deferral in your own summary too: never call such a run verified, and if the user wants a gate on future runs, point them at `{"dod":["node --test"]}` at the repo root (commit it -- an uncommitted config leaves the tree dirty and the next `round-start` rejects a dirty tree).

If a ledger for this ref is already `parked`, tell the user resuming will NOT auto-re-run parked findings; they must `review-cli.js unpark <ref> <findingId>` first. If the park has NO findings to unpark (a no-progress or budget-exhausted park -- e.g. the DoD kept failing with nothing for the review to fix), `unpark` has no target; once the underlying cause is resolved, `review-cli.js reset <ref>` discards the ledger so the next `round-start` begins a fresh run.

If the ledger is already `clean` and the user wants a SECOND review of the same ref -- typically with a different reviewer engine, for uncorrelated eyes -- use `review-cli.js rerun <ref> [--engine <name>]`, not `reset`. `rerun` archives the finished run (rounds, fix digest, kill rationales, gate ids) into the ledger's `runs[]` and re-arms it, so the next `round-start` drives a real round; the handoff reports every prior run. `reset` throws that history away. The new run starts blind on purpose: no findings are carried forward, because a second engine seeded with the first one's conclusions is no longer an independent look. `--engine <name>` is a free-text label recorded in the ledger and the handoff so the two runs are attributable.
