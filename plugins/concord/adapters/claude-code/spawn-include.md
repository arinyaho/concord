**Provider routing.** Parse `--reviewer <claude|codex|copilot>`, `--reviewer-model <model>`, `--fixer <claude|codex|copilot>`, and `--fixer-model <model>` from the invocation. Providers default to `claude`; models default to the selected provider's configured model. Use the reviewer selection for every review-class role and the fixer selection only for step 5. Carry the same selections through every round and resume. Reject missing values and unknown providers before `round-start`; never substitute another provider or model.

For a Claude role, use the native `Task`/`Agent` tool (whichever this session's harness exposes) with the `general-purpose` agent in a CLEAN context and pass the requested model explicitly when one was supplied. For a non-Claude role, start a clean non-interactive CLI process in the repository root:

- Codex: `codex exec --cd <repoRoot> --sandbox workspace-write --add-dir <stateDir> --skip-git-repo-check [--model <model>] "<prompt>"`
- Copilot: `copilot -C <repoRoot> -p "<prompt>" --silent --allow-all-tools --allow-all-paths --no-ask-user [--model <model>]`

The external CLI must write the requested artifact itself. Redirect its output away from the parent context and treat a missing executable, authentication/model failure, non-zero exit, missing artifact, or blocked operation as a harness failure. Allocate `telemetry-slot --engine claude-code` only for native Claude roles because external CLI evidence is not authenticated by Claude's agent hooks.

**Blocking a native Claude spawn.** For a sequential dependency ("wait for the file"), the spawn MUST block synchronously so the very next thing this session does is read the artifact the spawn just produced — never issue the dependent spawn and end the turn with nothing to wait on. If the spawn tool defaults to background/async execution (as the Agent tool does in some harnesses), explicitly force foreground/blocking mode on every such spawn (e.g. `run_in_background: false`) — do not rely on the tool's default. This applies identically whether this session is the top-level orchestrator or is itself a subagent that another session delegated to; a delegated subagent gets no special synchronous primitive, and if it fires an async spawn and ends its turn without a blocking wait, it goes idle with no way to resume itself — only an external nudge from whoever is listening for the notification advances it, which stalls the loop every round.

For a genuine parallel fan-out (the 5-lens panel, the 3-way adversarial verify) issued as multiple tool calls in one message: if this session is the top-level orchestrator, background/async spawns are fine — issue them together and wait for all artifact files before proceeding, same as external-CLI parallel spawns. If this session is itself a delegated subagent, do NOT fan out asynchronously — completion notifications for a subagent's own children are not reliably delivered back to that subagent's next turn (they may only reach the top-level session). Instead spawn each member of the batch as a separate blocking/foreground call, one after another, and proceed once all have returned.
