# Visual authoring

## Mine references before designing

- Inspect relevant internal decks and classify useful pages by role: cover, section divider, key message, architecture, process, comparison, evidence, scope, schedule, and close.
- Reuse visual grammar and proven composition patterns, not confidential content or stale claims.
- Distinguish portrait one-pagers from 16:9 presentation decks before comparing density.
- Detect image-only slides. Treat them as visual references, not construction templates, unless the requested output is intentionally fixed.
- Prefer about six to eight reusable content archetypes over one generic layout or dozens of one-off templates.

## Prototype the visual system

Create a fixed-canvas frontend render at the final aspect ratio before committing the design to Slides or PowerPoint. Prototype the theme and representative high-risk archetypes at minimum; prototype the whole deck only when consistency cannot be judged from those archetypes.

The prototype is a visual specification and QA surface, not the final deliverable. Use it to validate:

- hierarchy, spacing, alignment, contrast, and information density;
- font scale and line wrapping;
- diagrams, tables, charts, screenshots, icons, and image crops;
- the distinction and purpose of dark, light, and section backgrounds;
- whether each page has a clear visual center without becoming crowded.

“Full” means that meaningful visual structure owns the canvas. It does not mean filling blank space with smaller text and more boxes. Prefer one dominant diagram, metric, screenshot, table, or visual claim supported by secondary detail.

## Build a native, editable deck

- Create the theme, master, and layouts before bulk authoring.
- Put recurring backgrounds, branding, page numbers, headers, and footers on the master or layout.
- Keep titles, body text, tables, diagrams, borders, and data labels as native editable objects.
- Do not use a full-slide bitmap as a substitute for the master, layout, table borders, or editable content.
- Full-slide images are acceptable only when the image itself is intended, such as a photograph, texture, illustration, poster, or approved fixed one-pager.
- Use semantic color roles and make the meaning of dark and light backgrounds obvious. Do not alternate them decoratively.
- Use icons and images when they improve recognition, hierarchy, or recall; do not add them merely to decorate empty space.
- Keep font sizes harmonious. Remove accidental line breaks and manual wrapping that may fail under font substitution or export.

Architecture diagrams must reflect actual ownership and communication paths. Do not imply a connection with proximity or arrows when systems do not communicate. Give substantial solution components comparable visual weight even when one has fewer arrows or labels.

Interface slides should present real adoption paths. When both an SDK and API are supported and relevant, show both instead of presenting a single UI as though it were the product boundary.
