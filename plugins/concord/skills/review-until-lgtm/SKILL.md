# Review until LGTM

Use this after implementation and ordinary review are complete. It is a GitHub observation loop, not a replacement for `review-until-green`, and it does not edit source or merge a PR.

Set `STATE_CLI` to the state script path before polling. A development checkout uses `plugins/concord/hooks/review-lgtm-state.js`; the optional Copilot shortcut is `${COPILOT_PLUGIN_ROOT}/bin/review-lgtm-state.js`. It is not required: use this Node-based locator, which searches only installed plugin caches and never the reviewed checkout, validates the Concord plugin manifest, and deterministically selects the newest installed Concord version: `node -e "const fs=require('fs'),p=require('path'),o=require('os'),q=[p.join(o.homedir(),'.claude','plugins','cache'),p.join(o.homedir(),'.codex','plugins','cache'),p.join(o.homedir(),'.copilot')],c=[];function a(f){let d=p.dirname(f);for(;;){try{const m=JSON.parse(fs.readFileSync(p.join(d,'.codex-plugin','plugin.json'),'utf8'));if(m.name==='concord'&&typeof m.version==='string')c.push([m.version,f]);return}catch{}const u=p.dirname(d);if(u===d)return;d=u}}for(const d of q){const s=[d];while(s.length){const x=s.pop();let z;try{z=fs.readdirSync(x,{withFileTypes:true})}catch{continue}for(const e of z){const f=p.join(x,e.name);if(e.isFile()&&e.name==='review-lgtm-state.js'&&['hooks','bin'].includes(p.basename(p.dirname(f))))a(f);if(e.isDirectory())s.push(f)}}}c.sort((x,y)=>x[0].localeCompare(y[0],undefined,{numeric:true}));if(c.length)console.log(c[c.length-1][1]);else process.exit(1)"`. Set its one-line output as `STATE_CLI`, then invoke every verb as `node "$STATE_CLI" <verb> ...` (PowerShell: `node $STATE_CLI <verb> ...`; cmd.exe: `node "%STATE_CLI%" <verb> ...`), never by executing the `.js` path. Its markers live in the repository git directory, are keyed by PR number and exact head SHA, and make interruptions resumable.

## Observe the current review

1. Resolve the exact PR head SHA before requesting or judging a review. Inspect only reviews, summary comments, threads, and reactions attached to that exact commit; ignore stale results.
2. A matching review is one authored by GitHub Codex and bound to that SHA, regardless of its state. If no review object exists for that SHA, treat the bot's summary issue comment (marked by `<!-- codex-pull-request-review-summary -->`) as the source of matching activity: a row for that SHA that is not yet `✅ Completed` is in-progress matching review activity; do not request another review. That matching review activity owns the full bounded window through its durable PR marker. When matching activity is first observed and `status` has no `deadlineMs`, immediately run `node "$STATE_CLI" open-window <pr> <head-sha> 900`; the initial request window bounds both an in-progress review and a completed review waiting for its reaction.
3. Read `node "$STATE_CLI" status <pr> <head-sha>` before requesting. If no matching activity exists, run `node "$STATE_CLI" claim-initial-request <pr> <head-sha>` before requesting the initial review. Request it only when the result is `{"claimed":true}`; a `false` result must poll or reconcile the existing marker, never send a duplicate request. A claim without a sent marker belongs to its original session for a 15-minute lease: the request operation must complete or be cancelled before that lease expires. Reconcile matching activity while that lease remains, then run `node "$STATE_CLI" recover-initial-request <pr> <head-sha>` after it expires. Send only when that recovery result is `{"claimed":true}`; if that recovery claimant also disappears, wait its 15-minute lease and recover again. After either successful claim, mark it sent and open the initial window. Run `node "$STATE_CLI" mark-initial-requested <pr> <head-sha>` and immediately `node "$STATE_CLI" open-window <pr> <head-sha> 900` only after the request succeeds. On resume, an `initialRequested` marker with no `deadlineMs` must open the same initial window before polling. Do not send a request on every poll.
4. Poll GitHub with the configured authenticated GitHub CLI profile. Record the latest matching review associated with the latest request, its completion state, its summary, unresolved threads authored by that bot, and whether that bot added a +1 reaction to the PR itself — the reaction lands on the PR, never on the summary comment. Do not combine observations from separate reviews.
5. When a matching review object exists and completes, assemble one normalized observation for `record-review`: the review's numeric id, its URL, its `commit_id` — never an inline comment's `commit_id`, which can report a later commit than the review that created it — compared for exact-head matching against the PR's full `headRefOid`, `state` (`completed` or `in-progress`), the bot's LGTM-reaction presence, and one finding per unresolved bot thread plus one summary-level finding when the review body itself reports an issue, using the review URL. Count only unresolved bot threads created by this matching review as findings; an unresolved thread left over from an earlier head's review is not a finding for this head's review, though it stays visible to the human. Parse each finding's priority from its P1 or P2 badge text, defaulting to `null` when neither badge is present, and tag any signals from the closed set (`lifecycle`, `ledger`, `audit-privacy`, `provider-parity`, `ac-conflict`, `unsupported-test`) that apply. Run `node "$STATE_CLI" record-review <pr> <head-sha>` with that JSON on stdin before any retry claim; recording must happen before any retry claim because the retry claim path is blocked only once a review record exists for the head. If `record-review` exits non-zero or rejects the observation, stop and report it; never claim or request a review for that head afterward.
6. A clean Codex outcome creates no review object at all. Instead the bot's summary issue comment gets a table row for the head with Status `✅ Completed`, a Commit short SHA in backticks, and a completion time as `<relative-time datetime="...Z">`; about 2-3 seconds later the bot (`chatgpt-codex-connector[bot]`) adds a +1 reaction to the PR itself (`GET repos/<owner>/<repo>/issues/<pr>/reactions`). See "Decide and stop" for how this reports green.

## Decide and stop

When a matching Codex review object exists for the head, defer to `record-review`'s outcome rather than judging LGTM or thread state directly. `record-review` reports `needs-reconciliation` for any completed matching review with at least one unresolved bot thread or summary-level finding, even when the LGTM reaction (for example, `THUMBS_UP`) is present, and also when this call has no findings but a review record already exists for the head. Green and `completed-without-lgtm` are narrower than "review completed with no open bot threads": both additionally require no summary-level finding on this review and no existing review record for the head. Only then does the LGTM reaction decide between them — present is green, absent is `completed-without-lgtm`.

### Green with no review object

A clean Codex outcome creates no review object, so the rule above cannot apply. Report green from this path, at one poll, only when all four hold: (1) no Codex review has `commit_id` equal to the full `headRefOid`; (2) `node "$STATE_CLI" status <pr> <head-sha>`'s `reconciliation` is `null`; (3) every row of the bot-authored summary comment is `✅ Completed` and its Commit is a prefix of the full `headRefOid`; (4) a +1 reaction on the PR from the Codex bot login (`chatgpt-codex-connector[bot]`) has `created_at` at or after that row's completion `<relative-time datetime>`. A +1 created before the completion time never counts — it belongs to an earlier head. If 1-3 hold but no qualifying +1 appears by the persisted deadline, report `completed-without-lgtm`; that head stays eligible for `claim-retry`. In the green report, state the reaction's `created_at` and the row's completion time.

Once a record exists for a head, `node "$STATE_CLI" status <pr> <head-sha>` carries the reconciliation packet, whose `classification` is `light-implementation-eligible` for a bounded light-implementation handoff or `requires-architecture-review` for an architecture-review handoff, and the claim verbs — `claim-initial-request`, `recover-initial-request`, `claim-retry`, `recover-retry-request` — return `{"claimed":false,"reason":"needs-reconciliation"}` for that head. Only a human decision or a new head resumes observation; do not edit source or merge a PR to clear a finding.

Continue polling only until the current persisted deadline (`deadlineMs` for the initial request, `retryDeadlineMs` for the retry); a resumed session must call `node "$STATE_CLI" status <pr> <head-sha>` and reuse it rather than starting another window. If the deadline arrives while the matching review is still in progress, stop with the named external outcome `review-timeout`; do not retry an unfinished review.

After the initial deadline, only a completed-without-LGTM review may run `node "$STATE_CLI" claim-retry <pr> <head-sha>` before requesting another review. Request the one retry only when it returns `{"claimed":true}`, then run `node "$STATE_CLI" mark-retry-requested <pr> <head-sha>` and immediately `node "$STATE_CLI" open-retry-window <pr> <head-sha> 900` after the request succeeds. A retry claim records `retryClaimedAtMs`. If a resumed session finds a retry claim but no sent marker, reconcile it only with matching GitHub activity created at or after that timestamp; the original matching review cannot satisfy retry reconciliation. If matching retry-era activity exists, run `node "$STATE_CLI" mark-retry-requested <pr> <head-sha>` and `node "$STATE_CLI" open-retry-window <pr> <head-sha> 900` without sending another request. Hold that claim for its 15-minute lease; only after it expires run `node "$STATE_CLI" recover-retry-request <pr> <head-sha>`, and send only when it returns `{"claimed":true}`. A recovery claimant that disappears is recoverable after its own lease. On resume, a `retryRequested` marker with no `retryDeadlineMs` must open the retry window before polling. A sent marker forbids another retry for that exact head. Once the retry deadline expires without LGTM, stop and report `completed-without-lgtm`; do not retry indefinitely. A new head SHA is a new observation attempt. Do not fabricate a reaction or modify code.

## Handoff

State the PR, exact head SHA, matching review completion state, open bot-thread count, the +1 reaction's presence on the PR, persisted window deadline, and retry-claim result. For the no-review-object green path, state the qualifying +1's `created_at` and the summary row's completion time instead. A `completed-without-lgtm` result must remain visibly not green.

When a reconciliation record exists, report instead of the bare completion state: each recorded review's id and URL; each unresolved finding's URL with its P1/P2 priority (or none) and signals; the batch count; the classification (`light-implementation-eligible` or `requires-architecture-review`); the resume, revise, split, and defer choices; and that a human decision or a new head (a new commit) is required to proceed.
