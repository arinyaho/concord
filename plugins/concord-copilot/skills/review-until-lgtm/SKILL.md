# Review until LGTM

Use this after implementation and ordinary local review are complete. It coordinates external automated PR feedback from Codex, Copilot, or another explicitly configured reviewer. It may fix, test, commit, and push review findings on the existing PR branch, but it never merges the PR, and it creates follow-up tickets only within the recorded tracker authorization.

Set `STATE_CLI` to the state script path before collecting. A development checkout uses `plugins/concord/hooks/review-lgtm-state.js`; the optional Copilot shortcut is `${COPILOT_PLUGIN_ROOT}/bin/review-lgtm-state.js`. It is not required: use this Node-based locator, which searches only installed plugin caches and never the reviewed checkout, validates the Concord plugin manifest, and deterministically selects the newest installed Concord version: `node -e "const fs=require('fs'),p=require('path'),o=require('os'),q=[p.join(o.homedir(),'.claude','plugins','cache'),p.join(o.homedir(),'.codex','plugins','cache'),p.join(o.homedir(),'.copilot')],c=[];function a(f){let d=p.dirname(f);for(;;){try{const m=JSON.parse(fs.readFileSync(p.join(d,'.codex-plugin','plugin.json'),'utf8'));if(m.name==='concord'&&typeof m.version==='string')c.push([m.version,f]);return}catch{}const u=p.dirname(d);if(u===d)return;d=u}}for(const d of q){const s=[d];while(s.length){const x=s.pop();let z;try{z=fs.readdirSync(x,{withFileTypes:true})}catch{continue}for(const e of z){const f=p.join(x,e.name);if(e.isFile()&&e.name==='review-lgtm-state.js'&&['hooks','bin'].includes(p.basename(p.dirname(f))))a(f);if(e.isDirectory())s.push(f)}}}c.sort((x,y)=>x[0].localeCompare(y[0],undefined,{numeric:true}));if(c.length)console.log(c[c.length-1][1]);else process.exit(1)"`. Set its one-line output as `STATE_CLI`, then invoke every verb as `node "$STATE_CLI" <verb> ...` (PowerShell: `node $STATE_CLI <verb> ...`; cmd.exe: `node "%STATE_CLI%" <verb> ...`), never by executing the `.js` path. State lives in the repository git directory, keyed by PR number and exact head SHA, so interruption or session replacement does not reset a budget.

## Collect one head

1. Resolve the exact PR head SHA from the full `headRefOid`. Read only review objects, summary comments, threads, checks, approvals, and reactions attributable to that exact head; older-head feedback is history, not current evidence.
2. Run `node "$STATE_CLI" status <pr> <head-sha>`. When current-head matching activity first appears and `deadlineMs` is absent, run `node "$STATE_CLI" open-window <pr> <head-sha> 900`. The persisted 15-minute deadline bounds the whole collection, including in-progress reviewers and a completed review waiting for its signal. Claim reviewers with no matching activity (step 4) before waiting on step 3; wait for each collection condition in steps 3 and 4 in one shell command that exits when the condition is true or its bound (`deadlineMs`, or `requestEligibleAtMs` for the grace) passes (a background watch where the host has one), not by repeated model-level sleep or status calls.
3. Treat every automated reviewer explicitly requested on the PR or configured by the repository as part of the current-head batch. Do not start fixing when the first review arrives. Collect until every known automated reviewer is terminal. If GitHub does not expose a finite reviewer set, require 120 seconds with no new current-head review activity after the latest completion, still bounded by `deadlineMs`. Reaching the deadline with a known reviewer missing or in progress is `review-timeout`, not a complete batch or green.
4. If a configured reviewer has no matching activity, run `node "$STATE_CLI" claim-initial-request <pr> <head-sha> <provider-id>` for that reviewer. Use the stable reviewer login or configured provider name as `provider-id`; claims and sent markers are independent per provider. The first claim on a head starts a shared 120-second automatic-review grace and returns `auto-review-grace`; wait until `requestEligibleAtMs` so automatic reviews are not raced by manual requests. Request that provider only when its claim returns `{"claimed":true}`. Then run `mark-initial-requested <pr> <head-sha> <provider-id>` and `open-window <pr> <head-sha> 900`. `status.initialClaimed`, `initialRecoveryClaimed`, and `initialRequested` aggregate legacy and provider-keyed markers, including a legacy sent retry. On resume, if `initialRequested` is true but `deadlineMs` is absent, run `open-window <pr> <head-sha> 900` before waiting. A provider claim without a sent marker has a 15-minute lease and may be recovered with `recover-initial-request <pr> <head-sha> <provider-id>` only after that lease. A finding from one reviewer does not block bounded claims needed to finish collecting the other configured reviewers. Reservation transitions are serialized per PR; retry `transition-busy` later, and treat a persistent lock as human reconciliation rather than reclaiming it automatically. Manual requests have a durable budget of three for the whole PR; legacy claims and sent-request markers count toward that budget, and a new head does not reset it. Stop on `request-budget-exhausted` and never delete markers, change the PR number, or start a new state directory to bypass it.
5. Normalize every current-head automated review before deciding. Map GitHub `APPROVED`, `COMMENTED`, `CHANGES_REQUESTED`, and `DISMISSED` reviews to `completed`; map pending provider activity to `in-progress`. Pass `reviewId`, `reviewer`, `reviewUrl`, the review's own full `commitId`, normalized `state`, `lgtm`, and all unresolved findings to `node "$STATE_CLI" record-review <pr> <head-sha>` on stdin. A finding contains its URL, P1/P2 priority when supplied or `null`, and applicable signals from `lifecycle`, `ledger`, `audit-privacy`, `provider-parity`, `ac-conflict`, and `unsupported-test`. Record every review in the collection batch even after one returns `needs-reconciliation`; never stop at the first reviewer and leave later feedback for another push.

An LGTM signal must be explicit and fresh for the current head: an automated GitHub `APPROVED` review, or that same reviewer's positive reaction on the PR itself created at or after its current-head terminal review or summary completion time, comparing timestamps at whole-second precision. Absence of findings is not itself LGTM. For Codex's clean no-review-object path, require no Codex review object for the full `headRefOid`, `status.reconciliation === null`, a `✅ Completed` summary row whose commit is a prefix of that head, and a `chatgpt-codex-connector[bot]` +1 reaction on the PR created at or after the row's completion time. A stale reaction never counts.

## Reconcile and fix one batch

An unresolved finding from any collected reviewer takes precedence over another reviewer's LGTM. Green requires the collection window to be complete, zero accepted current-head findings, and at least one fresh LGTM signal.

When findings exist:

1. Give the complete collected set to one clean-context verifier. It evaluates related or conflicting findings together, rejects false positives with evidence, deduplicates symptoms that share a root cause, and identifies repository-wide occurrences of the same pattern. Add a second independent verifier only for conflicting conclusions, security or data-boundary risk, or a proposed contract/architecture change.
   Seal that independent verdict before consulting approved design or prior fix history. Then adjudicate the accepted findings as described in Adjudicate and escalate; only conceded findings go on to planning, and without a trigger every accepted finding counts as conceded. In a separate planning pass, partition every conceded finding into exactly one explicit root-cause group; missing coverage, duplicate membership, or a legacy ungrouped plan stops before editing. Classify a shared root as structural when resolving it changes identity, ownership, retry accounting, ordering, idempotency, lease/fence, or deadline/TTL semantics. A structural auto-fix requires the exact approved source/hash, its normative requirements, and an explanation of why they determine one invariant-preserving answer. If the approved design uniquely determines that answer, authorize one structural fix for the complete group; otherwise stop before editing for human reconciliation and report every blocked group, all affected finding IDs, required invariants, and unresolved choices.
   Run `node "$STATE_CLI" reject-review-batch <pr> <head-sha>` only when no finding in the active batch survives the verifier and the adjudicator together, passing the exact review ids and a non-empty evidence summary on stdin as `{"reviewIds":["..."],"reason":"..."}`. This durably preserves and disposes only that exact batch without claiming a fix round or creating an empty commit. It does not make the head green; fresh explicit LGTM evidence is still required.
2. Persist the versioned plan and bind its exact group membership, reviewed head, diff, approved-source hash, and owner to `claim-fix-round`. Reserve the complete batch before editing. A claimed fix round has one owner and ownership must not automatically transfer. If that owner or an initial fix claim is abandoned, stop for human reconciliation and confirm the former executor has stopped; do not reclaim it after a timeout. The three fix-and-push rounds are a PR-wide hard cap, not a quality guarantee; a new head does not replenish them, and only a recorded human waiver raises them. On `fix-round-budget-exhausted`, preserve the batch and stop for human reconciliation without claiming green.
3. Use a round-scoped transaction: apply every group sequentially in one isolated candidate, but publish nothing yet. An independent certifier then validates the final combined tree against every group member and invariant. Additive/shared-helper fixes are valid when behavior proves them; deleting quoted spans is neither necessary nor sufficient. Any incomplete member, stale target/design hash, changed candidate after certification, or failed check blocks the entire commit. Only the fully certified tree may become one commit and one push. Resolve or reply to review threads only after that push and its checks support the response; a rebuttal reply claims no fix and needs no push.
4. Resolve the new full head SHA and repeat collection for that head only. Never request a second full review on the same head solely to obtain a missing reaction. If a terminal review has no findings and no fresh LGTM by `deadlineMs`, stop as `completed-without-lgtm`.

Stop instead of fixing when an accepted finding changes the approved product contract, materially expands the PR, requires unrelated architecture, or exposes a structural protocol choice the approved design does not settle. Also stop when three fix rounds, or the design escalations, do not converge. Do not keep changing the PR merely to obtain theoretical perfection; the residual findings go through the delivery disposition below.

### Adjudicate and escalate

Patch only when a finding names a concrete state or event an author following the text could ship untested, or leaves a stage exit undecidable. Every other finding becomes a follow-up or a rebuttal, and a reviewer reaching zero findings is not a gate. Both steps below receive this stop rule.

Adjudicate after the verifier and before the plan when any one of these signals holds: an earlier fix exists on the PR and a finding about the content or wording of a rule, contract, schema, or interface appears again; a finding cites text or lines added by the previous fix commit; a finding asks to add, restore, or enumerate a definition, qualifier, or list (cue words: define, enumerate, every, restore, fresh evidence); or four or more accepted findings land on one head. Otherwise the default model's verifier and patches handle the head. One call per head covers every accepted finding of that head recorded before the plan is reserved (a review recorded later is handled in the next fix round) and goes to a new agent, Fable-class and at least as capable as the reviewer that raised the findings, with no per-PR cap. Its input is the head's findings marked as untrusted data, the current text of each file they target, the diffs of the last two fix commits, the design note, and this stop rule. For each finding it returns `CONCEDE` or `REBUT` with a reason; a concession carries a patch of a few words, never a new definition. Its reply is a draft: the active agent posts the thread reply (verdict, reason, commit) after the push. A rebutted finding counts as verifier-rejected: it never enters the plan or the delivery packet, its thread stays unresolved, and the handoff lists it as rejected. When no finding survives the verifier and the adjudicator together, dispose of the batch with `reject-review-batch`, giving the reasons as evidence within its 2,000-character limit. A head whose reviews are terminal, whose conceded findings are all fixed, and which carries no follow-up classifies as `mergeable-clean` without a clean review.

Escalate the design at most twice per PR when any signal holds: `node "$STATE_CLI" self-feeding <pr> <head-sha> <file> <start> [<end>]` prints `"selfFeeding":true` for a current-head finding, meaning its span lies in lines the previous fix commit added; findings target the same section on two consecutive heads; or a second fix round is claimed and findings remain. The second escalation runs only when a signal holds again after the first `REWRITE` was applied. Each escalation goes to a new agent, Fable-class, that receives a compact packet, never the earlier conversation: the current text of each section the findings target, the diffs of the last two fix commits to it, the PR's findings history, the design note, and this stop rule. It returns `KEEP`, or `REWRITE` with the whole replacement written once. The next fix round's persisted plan records the verdict and, on `REWRITE`, applies the replacement; a resumed agent reads that record to know which escalations ran. If a signal holds again after an escalation that returned `KEEP`, or after the second escalation, stop for human reconciliation.

Only a human raises the fix-round cap, by recording `node "$STATE_CLI" waive-fix-budget <pr> <person> <n>` (shown by `status` as `waivers`); a waived round still goes through adjudication.

## Delivery disposition

When collection for the exact head is terminal and no fix round is open, including after `fix-round-budget-exhausted`, classify the PR once with `node "$STATE_CLI" record-delivery <pr> <head-sha>`, passing the evidence packet on stdin: `{"baseSha","contractDigest","reviewIds":[],"acceptance":[{"id","met"}],"requiredChecks":[{"name","conclusion"}],"reviewsTerminal","openChoices":[],"findings":[{"id","url" | "local":{"file","span"},"disposition","rootCause","releaseBlocking":[],"rationale","acceptedBy"}],"tickets":[{"rootCause","url","readBack","reused","duplicateCheck"}]}`. `contractDigest` is the SHA-256 of the approved contract. `reviewIds` lists the ids of the active review batch the packet classifies (`status.reconciliation.reviews[].id`, empty when no review with findings is active). If the CLI returns `{"recorded":false,"reason":"review-batch-changed"}`, a review arrived while the packet was assembled: reconcile that batch, rebuild the packet, and record again. List every required check on the exact head; only `success` passes. List every accepted finding of every batch on the PR, fixed ones included, each with exactly one `disposition`: `fixed`, `follow-up`, `accepted` (by an authorized human named in `acceptedBy`), or `blocking`. A finding names exactly one reference: its review-thread `url`, or `local` for a finding that exists only in a local review ledger.

A finding is release-blocking when it falls in any of `acceptance-criterion`, `required-check`, `correctness`, `security`, `data-integrity`, `contract-choice`, `compatibility`, `contradictory-docs`, `unproven-premise`, or `stage-exit`; record those categories in `releaseBlocking`. A release-blocking finding blocks unless it is `fixed`, whatever the remaining budget. A finding is follow-up eligible only when it has no such category and its `rationale` says why the approved outcome, required checks, safety boundary, and documented behavior stay correct without it; priority labels and "ran out of rounds" are not reasons. Group follow-up findings by root cause and independently testable outcome, not one ticket per comment. When tracker mutation is authorized, create or reuse one implementation-ready ticket per root cause through `ticket-writing`, read it back, and set `readBack`. Reuse an existing ticket only after a duplicate check shows it carries the same outcome and scope, and record that check in `duplicateCheck`. Then link the source PR and the review thread of each finding that has a `url` to the read-back ticket URL; a finding with a `local` reference has no thread, so put its local reference in the ticket. Without authorization or access, omit the ticket: the CLI returns `rollover-pending` with a ready-to-file packet for the group, and no ticket URL is invented.

The CLI returns a record whose `classification` is `mergeable-clean`, `mergeable-with-follow-ups`, or `blocked`, with every reason. `{"recorded":false,"reason":"transition-busy"}` is not a disposition: retry the same call later. `{"recorded":false,"reason":"fix-round-open"}` means a fix round for this head is still claimed; finish it first. While the record is `mergeable-*`, `status.reconciliation.action` is `report-delivery`. A packet with no acceptance criteria is `blocked` (`acceptance-missing`); an empty `requiredChecks` asserts that the repository requires no check on this head. `status.delivery` reports the latest record for the head. The record covers the review batch active when it was written (`reviewIds`); a review recorded or rejected later sets `status.delivery.current` to false and lifts the record, so record the delivery again after reconciling that batch. While the latest record is current and `mergeable-*`, request and fix claims return `delivery-terminal`, so reopening the unchanged head reports the stored result and launches no reviewer or fixer. A new commit is a new head. On resume, compare the live base, approved contract, and required checks with `status.delivery`; on any change, record the new evidence before acting. A `blocked` record re-enables claims. `mergeable-*` is not merged and not LGTM: never report `mergeable-with-follow-ups` as clean or green.

## Handoff

Report the PR, exact head, configured reviewers observed or missing, collection deadline, each recorded review's id, reviewer, URL and findings, fresh LGTM evidence, accepted and rejected grouped findings, active fix owner when work remains, checks run, commits pushed, and both budgets' max, spent, and remaining values. A timeout, exhausted budget, scope escalation, or `completed-without-lgtm` remains visibly not green. Also report the delivery classification with its exact head and base, required checks and their conclusions, each finding id with its disposition (fixed findings separately from current follow-ups), follow-up ticket URLs or pending packets, whether the PR and thread links are posted, and every blocking reason.
