The review CLI is invoked as `node "<review-cli>" <verb> ...`, where `<review-cli>` is the harness-resolved path to the review CLI script (each packaging layer wires this to its own copy of the script). It is the deterministic authority on rounds, dedupe, and termination; you drive it and spawn the review/fix subagents, but you make NO judgement about findings, DoD, or when to stop -- the CLI decides.

Concord IS the reviewer. The findings for every round come from the review subagents YOU spawn against the diff (steps 2-3) -- never from a bot, CI check, or human review posted on the PR. Do NOT `gh pr ready` and wait, do NOT poll or `ScheduleWakeup` for a Codex/Copilot/CI review to land, and do NOT treat any external review as this loop's rounds or gate. If the target happens to be a PR that also gets bot reviews, ignore them here; they are not your input and waiting on them is the failure this loop exists to replace. Once `round-start` says `work`, the very next thing you do is dispatch this round's review subagents in THIS session.

A 30-second foreground wait or empty output is not a terminal result. While an owned driver process is alive, inspect that process and ledger and keep waiting; a non-terminal ledger without a live driver is a stopped driver, so report it rather than waiting indefinitely. Report a terminal result only from a durable terminal disposition or the ledger's bounded no-progress decision. Before declaring a reviewer blocked because its skill cannot be found, resolve the installed skill path recursively to the actual `SKILL.md`; do not assume a flat install layout.

Arguments: `<arguments>` -- the harness-resolved invocation arguments; each packaging layer wires this to its own argument-substitution token (the same way `<review-cli>` is wired to the CLI path).

Remove the recognized provider/model option-value pairs before determining the target ref: empty -> current branch (`git branch --show-current`); `resume <ref>` -> the ref after `resume`; else the first positional argument. Optional base ref is the second positional token (default the repo's remote main branch, `origin/<main>` -- a local base can be stale (behind its remote), which sweeps unrelated merged changes into the diff).

To review a local file or document instead of a git diff (a design/spec `.md`, a note -- reviewable even in a directory that is not a git repository), pass a single `file:<path-or-glob>` token as the ref, where `<path-or-glob>` is a literal path OR a simple single-`*` glob resolved against the repo root: `round-start file:note.md` or `round-start file:*.md` (the glob pulls in every match, concatenated in sorted order). This is the ONLY file-target form -- there is no `--files` flag. A file target has no base and no DoD; `round-start` reports `targetType: 'file'` and the per-round flow branches on it (see step 2).

Broad review is ON by default and needs no flag: the CLI fires the gate pair on the first round only, so it costs two subagents once per run, not per round. Pass nothing. The one case that needs a flag is an explicit opt-out -- if the arguments contain the literal token `--no-broad`, or the user asked for a diff-local-only/fast review in their own words, pass `--no-broad` to every `round-start` call for the rest of this run (harmless to repeat -- the opt-out is sticky). `--broad`/`--gate` remain accepted and re-arm a run that opted out earlier; do not add them on your own initiative, they change nothing on a default git run. One exception where they do change something: a `file:` target is broad-disarmed by default (the gate pair's prompt is written against a git diff and sweeps the repository, which a doc review does not need), so pass `--broad` only if the user explicitly wants the tree swept against that document.

Also check whether this invocation asked to run without an executable DoD gate: if the arguments contain the literal token `--no-dod`, pass `--no-dod` to every `round-start` call for the rest of this run (harmless to repeat -- the deferral is sticky once applied). The review gates still run; otherwise the executable DoD runs once after review convergence, immediately before the clean disposition, rather than once per round. Pass this flag ONLY when the user's invocation asked for it. Never add `--no-dod` on your own initiative to get past a failing gate -- skipping a check that is failing is the user's decision, never yours. (You do not need it for a repo with no `review.config.json`: that case already defers on its own.) A DoD command that exits 78 (EX_CONFIG) is reporting an environment or setup error, not a test failure: the gate still fails and the handoff labels it, so relay it as an environment problem to fix (network, registry, missing tool) rather than as a defect in the reviewed change, and never skip the gate to get past it.

**Append this clause verbatim to EVERY review-class subagent prompt you spawn** -- correctness, verify, plan, intent, gate-review, gate-verify, and certify. The loop makes reviewers hunt verifier-gaming in the diff; this is the same guard pointed at the reviewer's own evidence, and nothing else in the loop provides it:

> If you were told to establish something by a specific method -- measure it, run it, execute the check -- and you cannot run that tool (missing, denied by permissions or sandbox, crashed, timed out), do NOT quietly substitute a weaker method and do NOT stay silent. Add `"blocked": ["<tool>: <what failed>"]` to your artifact and stop there -- keep `"status":"ok"` and leave the arrays empty; `blocked` is what fails the round, there is no `"status":"blocked"`. That fails the round loudly, which is the correct outcome; a schema-valid verdict from a check you never actually ran is indistinguishable from a real one and is worse than a failure.

Never soften that clause, and never accept an artifact from a reviewer you know was blocked -- a non-empty `blocked` is terminal wherever the CLI reads the artifact, precisely so a degraded reviewer cannot produce a verdict.

**Initiative budget.** If the arguments carry `--initiative-run-key <key> --initiative-state-dir <absolute-dir> --initiative-max-launches <n> --initiative-max-rounds <n> [--initiative-mode <base|lite>]`, this run shares a durable launch and round budget with every other reviewer of the same repository. Pass those four options, unchanged, to EVERY review-cli verb, and call `node "<review-cli>" reserve <ref> <role> [--count <k>]` immediately BEFORE each launch or concurrent fan-out, launching only when it prints `"status":"granted"`. The roles are `correctness`, `verify`, `plan`, `intent`, `gate-review`, `gate-verify`, `fix`, and `certify`; sequential fix and certification launches reserve one slot immediately before each launch. A batch is granted or denied as a unit; on `"status":"denied"` or `"status":"reconciliation-required"`, nothing was consumed and you MUST NOT launch. Every retry is a new launch and must be reserved again. Reservation is enforced at evidence acceptance: `plan-fixes`, `record`, and `commit-fix` reject an artifact whose role has no matching reservation and fail the run closed. Never write an artifact yourself to bypass that rejection. After a successful keyed target operation, every later mutating verb must carry the complete initiative options. `reset` is forbidden for an initiative target. On `budget-exhausted`, stop: never increase budgets or change the run key yourself, and never fall back to an unkeyed call. The CLI persists a recovery marker; after human reconciliation, the operator may use the printed `carry <ref> --from-run-key <old-key>` command with a new key's initiative options to reuse hash-verified completed artifacts. Never use `carry` merely to refresh context or evade a budget.

**Session handoff.** For an initiative-bound driver, inherit `--session-handoff off|suggest|stop-at-checkpoint` from its packet (default `suggest`). Remove this option-value pair before parsing target/base; pass it only to `session-checkpoint`, not to other review verbs. Count caller-observed input context when exposed, tool calls in this driver context, and consecutive calls without meaningful progress (new verified evidence, a resolved decision, committed changes or completed gates reset that count). At 128,000 input tokens, 50 tool calls, or 10 no-progress calls, finish the round and drain owned children before the next round. Cache-read totals are not input context. Persist distinct durable state/handoff files with approved source identities, revisions, blockers, target ledger directory, exact next CLI step, original initiative options, completed role artifacts and existing reservations. Write a bounded absolute JSON packet with `scope: "review"`, `boundary: "round-complete"`, `liveWorkers: []`, absolute `statePath` and `handoffPath`, a verified `nextAction` of at most 1,000 characters, and `observations: {inputTokens, toolCalls, noProgressCalls}` (null for unmeasured counts). Call `node "<review-cli>" session-checkpoint <absolute-packet.json> --session-handoff <policy>` with the unchanged initiative options. `continue` proceeds; `defer` drains workers and finishes the boundary before retrying; `suggest` presents the saved prompt/checkpoint once per distinct trigger and continues; `stop` reads both artifacts back, presents the continuation prompt and paths, then returns to the orchestrator without another round. `off` bypasses these efficiency checkpoints. Errors must be reported as failed handoffs. The CLI does not terminate host processes. Resume verifies source hashes/versions, scope, authorization, head/base, blockers and live budget before the recorded next step; consume completed artifacts instead of relaunching reserved roles. Context replacement never resets a ledger, passes a gate, increases budgets or revives a terminal/reconciliation disposition.

**Initiative mode.** The run ledger stores the delivery mode: `base` (the default, full review) or `lite` (opt-in). The caller states it when the run is first opened by adding `--initiative-mode <base|lite>` to the four initiative options; a mode that disagrees with the stored one is refused with `run mode is <mode>`, so a later call may repeat it or omit it. In a lite run `round-start` prints `mode: "lite"` and `gateMode: "design-conformance"`, rejects `--broad`, `--gate` and `--no-broad`, and fires one design-conformance gate subagent on the first round instead of the base gate pair. `plan-fixes` accepts only `gate:design-conformance:` ids from a lite gate and handles them as material findings (reconciliation, no fixer).

> Review <stateDir>/round-<n>-diff.txt for design-conformance gaps only: places where the change does not do what the design/plan/AC at <stateDir>/intent-<slug>.md (read it if it exists) requires, or does something it forbids. You MAY Read/Grep the repository. Report only gate: findings, and every ID MUST be gate:design-conformance:<slug>. Do not report ac-coverage, cross-context or silent-gap findings. Each finding needs file, span/evidence anchor, requirement text when available, and summary. If this finding is an instance of a pattern likely to recur elsewhere in the repository (a value, name, or reference that should be mirrored across multiple files), sweep the whole repository for every other file matching that same pattern in this same pass and report each occurrence as its own finding -- do not stop at the first instance and leave the rest for a later round to catch one at a time.

A lite run that has not made its first launch can be switched to base with `node "<review-cli>" escalate <trigger>`, called with the four initiative options carrying the base budgets; `<trigger>` is one of `public-api`, `schema`, `security`, `legal`, `cross-package`, `cross-repository`, `multi-outcome`, `unsettled-contract`, `migration`. The trigger is recorded in the run ledger and the stored budgets are replaced by the ones passed. After the first launch `escalate` is refused: stop for reconciliation. Only after that reconciliation may the caller start a new base run key in a separate target review state directory, retaining the old target ledger as evidence. Start the ref normally in that directory when no ledger exists; do not change the binding of the old target or use a new key to bypass exhaustion. `node "<review-cli>" finalise` ends the run, writes its completion report (`initiative-report-<sha256 of the run key>/report.json` and `report.md`) and rebuilds the project index `initiative-reports.jsonl`, all in the initiative state directory, holding only allowlisted aggregates (hashed ids, counts, bounded finding classes and roles, token totals, elapsed time), and a run that never finalises has no report and is absent from the index; if rendering fails the run is already terminal, so fix the named cause and run `finalise` again; and `node "<review-cli>" consume <claim>` acknowledges a delivered disposition: when `record` records a disposition it prints its delivery claim as `initiative.claim`, and `consume` fails with `no unconsumed delivery` when the claim is unknown or already acknowledged. `finalise`, `consume` and `escalate` take the four initiative options (and no ref) and act on the run, not on a target.

Immediately before a spawn whose harness adapter exposes authenticated telemetry, allocate the exact output artifact through `telemetry-slot` using the engine named by that adapter. Do not allocate synthetic slots for provider CLIs or native hosts that lack stable usage evidence. The adapter's routing instructions are authoritative for whether a slot exists; allocation never changes prompt or launch ordering.

Run this loop. Do each step in order; do not skip, reorder, or improvise termination.

1. `node "<review-cli>" round-start <ref> [base] [--reviewer <provider>] [--reviewer-model <model>] [--fixer <provider>] [--fixer-model <model>] [--no-broad] [--no-dod]`
   - `decision: "terminal"` or `"no-op"` -> stop; report the CLI's message.
   - `decision: "work"` -> continue: proceed straight to step 2 in THIS session. Do not pause, defer, or wait on anything external first. Note the `round` number `n`, the `stateDir` path it prints (`stateDir` is the CLI-owned directory for this run's artifacts; every path below is relative to it), and the `dodPending` and `dodDeferred` booleans. `dodPending:true` means the configured DoD is reserved for the final clean boundary; reviewers do not run it themselves. `dodDeferred:true` means no executable gate will run and must never be described as passed. On a resumed round, skip every role named by `completedArtifacts`; for each still-pending role named by `retryArtifacts`, use that persisted corrective prompt for its one retry instead of the normal role prompt, then normalize it. Never re-run a completed role or turn a persisted retry into a second retry.
2. Read the file at `<stateDir>/round-<n>-diff.txt` (the file round-start just wrote -- for a git target this is a diff; for a file target this is the current content of the target file). Reserve `correctness` (and `verify`, `intent`, `gate-review`, `gate-verify` for the roles this round will launch), then spawn ONE correctness review subagent per the harness spawn-include (clean context -- do not paste your own prior reasoning). The prompt to give it depends on `targetType` from the round-start output:

   **If `round-start` reported `targetType: 'file'` (doc review):** Use this DOC-REVIEW prompt instead of the code-correctness prompt below. Note that a file target has no DoD step (round-start reported `dodPassed: true` as a no-op) and fixes are plain file edits by the caller -- `commit-fix` is skipped for file targets, so skip step 5's `commit-fix` call.

   > Review the document at `<stateDir>/round-<n>-diff.txt` (the current content of the target file, not a diff). Find: internal contradictions, claims made without supporting evidence or reference, placeholders/TBDs/TODOs, over-claims (asserting something is proven/complete when the text does not establish it), and buried or omitted limitations. You are also handed the prior round's still-open findings -- for the SAME objection, REUSE its `id` verbatim so it dedups; only mint a new `id` for a genuinely new objection. Write ONLY to `<stateDir>/round-<n>-correctness.json`: `{ "status":"ok", "examined":["<file>"], "findings":[ {"id":"docreview:<stable-slug>","gate":"correctness","file":"<path>","span":"<exact offending text>","summary":"<one sentence>"} ] }` -- empty findings if nothing.

   **If `round-start` reported `targetType: 'git'` (code review, default):** Instruct the subagent to review the diff for correctness bugs, reuse/simplification/efficiency, AND verifier-gaming (hardcoded literals matching test inputs, weakened/deleted assertions, output emitted before the check runs, whether a fix explains WHY a test passes not just that it does). If `round-start` reported `dodPending:true`, tell it the configured DoD will run once after review convergence and it MUST NOT run the build or test suite itself; spend the review budget on logic bugs, reuse, and verifier-gaming. If `dodDeferred:true`, say that no executable gate will run; one focused existing check is acceptable only when needed to substantiate a specific finding, but do not run the full suite. Ignore any intent-*.md file in the state directory; it is not part of your input. Review only the diff and the surrounding code. Tell it that uncertainty is not a reason to withhold a finding -- the verify subagent in step 3 rejects false positives, so a finding it is unsure about costs nothing to raise. Triviality is different and it should still use judgment there: a real-but-minor finding is not a false positive, so verify must keep it, it routes to a fixer, and a fixer that honestly reports no change was warranted parks the run for a human and charges the park budget. It MUST write ONLY to `<stateDir>/round-<n>-correctness.json` the JSON `{ "status":"ok", "examined":[<every changed file path it looked at>], "findings":[ {"id":"correctness:<stable-slug>","gate":"correctness","file":"<path>","span":"<exact offending text>","summary":"<one sentence>"} ] }` -- empty `findings` array if nothing. The `id` is a stable slug reused for the same bug across rounds.
3. Only after the correctness subagent from step 2 has finished, spawn ONE verify subagent (clean context). On a base round where `gateApplied` is true, also wait for `round-<n>-gate.json` and give verify both candidate artifacts as one batch; verify still writes verdicts only for `correctness:`/`docreview:` candidates. Verify MUST ignore `intent-*.md` and `round-<n>-history.json`: seal the independent verdict before design or prior conclusions can influence it. Write ONLY `{ "status":"ok", "rejected":[ {"id":"<id>","reason":"<one-line evidence>"} ], "findings":[] }` to `<stateDir>/round-<n>-verify.json`. A rejection without a reason is invalid. Never run verify before its finder input exists.

   If `round-start` reported `intentApplied: true`, ALSO spawn a separate intent-detector subagent per the harness spawn-include (in parallel with the correctness -> verify pair -- it doesn't depend on either's output). Its prompt is the following, with the blocked-tool clause above appended, and with round-start's `priorIntentIds` list pasted in verbatim where the prompt refers to it:

   > You are a design-conformance detector. Inputs: the diff at `<stateDir>/round-<n>-diff.txt` and the stated requirements at `<stateDir>/intent-<slug>.md`. Write a JSON file to `<stateDir>/round-<n>-intent.json` of the form `{ "status": "ok", "findings": [ ... ] }`.
   >
   > You are also handed `priorIntentIds` from `round-start` -- the still-open intent findings from the previous round. For the SAME objection against the SAME requirement, REUSE that `id` verbatim so the human re-reading the handoff recognises it as the objection they already saw; mint a new `id` ONLY for a genuinely new objection. Nothing dedupes intent findings by id, so a re-slugged repeat reads as a second, new problem.
   >
   > Raise a finding ONLY for an active contradiction of an explicit, stated requirement, on a line the diff added or changed: the intent states X unambiguously and a changed line does not-X. Each finding is `{ "id": "intent:<slug>", "file": "<changed file path>", "span": "<the exact contradicting changed line>", "requirement": "<the verbatim requirement text it contradicts>", "summary": "<one line>" }`. The `id` MUST start with `intent:`. The `file` MUST be one the diff changed.
   >
   > Do NOT raise: a requirement the diff is merely silent on (missing/incomplete); a contradiction on an unchanged file; "is this the right architecture / should this be refactored / does this match the spirit"; a requirement quoted from a non-normative part of the intent (a rejected alternative, background, an example of what not to do). If unsure whether something is an active contradiction or a matter of design taste, do not raise it. These findings are reported to a human, never auto-fixed.
   >
   > If there are no contradictions, write `{ "status": "ok", "findings": [] }`.

   If `round-start` reported `gateApplied: true` in base mode (normally round 1 only), launch correctness and **gate-review** in parallel, then wait for BOTH artifacts. Next launch verify and **gate-verify** in parallel. Both verifiers receive both candidate artifacts as one batch so they can identify shared roots and conflicts, while each writes verdicts only for its own namespace. Never start either verifier before both finder artifacts exist. Unlike the correctness finder, the gate finder MAY Read and Grep the whole repository and MUST consider the design/plan/AC in `intent-<slug>.md` when present.

   In a lite run (`round-start` reported `gateMode: "design-conformance"`) spawn only the lite gate-review described under Initiative mode, with no gate-verify.

   **gate-review** (spawn per the harness spawn-include, clean context): "Review the diff at `<stateDir>/round-<n>-diff.txt` for defects a diff-local reviewer structurally cannot catch: design-conformance gaps, silent gaps (the design/plan/AC requires something the code omits), AC-coverage gaps, cross-context violations (an unchanged file -- sibling or cross-repo -- whose invariant a changed line breaks), and threat-model gaps. You MAY Read/Grep the repository and MUST read `<stateDir>/intent-<slug>.md` if present for the design/AC. Write ONLY `{ "status":"ok", "findings":[ {"id":"gate:<class>:<slug>","file":"<path, may be unchanged>","span":"<anchor>","requirement":"<the design/AC text it fails, if any>","summary":"<one sentence>"} ] }` to `<stateDir>/round-<n>-gate.json`. `<class>` is one of cross-context | silent-gap | ac-coverage | design-conformance | threat-model. If this finding is an instance of a pattern likely to recur elsewhere in the repository (a value, name, or reference that should be mirrored across multiple files), sweep the whole repository for every other file matching that same pattern in this same pass and report each occurrence as its own finding -- do not stop at the first instance and leave the rest for a later round to catch one at a time. Empty findings if nothing. Report every gap you find, including ones you are uncertain about: a separate gate-verify pass rejects false positives, so your job here is coverage, not filtering. Report only; you never fix."

   **gate-verify** (spawn per the harness spawn-include, clean context, a DIFFERENT lens): "Re-review the candidate findings in `<stateDir>/round-<n>-gate.json` together with `<stateDir>/round-<n>-correctness.json` against the diff and repository. Evaluate related or conflicting findings as one batch. Use correctness candidates only as context when evaluating gate candidates. Your artifact may disposition only gate:* candidate IDs. Do not copy, accept, or reject correctness:* or docreview:* IDs in this artifact; their disposition belongs to the correctness verifier. Reject false positives and design-taste objections; keep only real, actionable gaps. You may also add a genuinely new `gate:` finding. Write ONLY `{ "status":"ok", "rejected":[ {"id":"<gate: finding id>","reason":"<one-line evidence>"} ], "findings":[] }` to `<stateDir>/round-<n>-gate-verify.json`."

4. After every independent reviewer has finished, reserve and spawn ONE `plan` subagent. It reads the sealed correctness/verify artifacts, then reads `<stateDir>/round-<n>-history.json` and `intent-<slug>.md` when present. It must partition every surviving finding into exactly one explicit v2 group with `groupId`, `findingIds`, `rootCause`, `invariants`, `changeClass`, `structuralEffects`, and `action`. Structural `action:"fix"` additionally requires the exact approved source/hash, normative requirements, and why they determine one answer; otherwise use `action:"reconcile"`. It MUST write ONLY the v2 plan JSON to `<stateDir>/round-<n>-plan.json`. Normalize that artifact, then run `node "<review-cli>" plan-fixes <ref>`. If reconciliation is returned, run `record` once and stop without launching a fixer. Missing classification or a legacy plan is a harness failure, never a singleton fallback.
5. For each authorized group, reserve one `fix` launch and apply one coherent change for its complete membership. The fixer MUST write ONLY its result JSON to `<stateDir>/round-<n>-fix-<safe-group-id>.json` with the exact `groupId` and every edited file. Then reserve an independent `certify` launch. The certifier checks every member and invariant against the actual candidate, records focused evidence, hashes the exact bytes of every edited file, and MUST write ONLY its certificate JSON to `<stateDir>/round-<n>-certify-<safe-id>.json`; span disappearance is neither necessary nor sufficient. For `transactionScope:"group"`, run `commit-fix <ref> <groupId>` only after that group's certificate. For `transactionScope:"round"`, run all group fixers sequentially in the same candidate, certify the complete plan once, and run `commit-fix <ref> <planId>` once. A partial or stale certificate never commits. File targets use explicit singleton groups and certified content but skip the Git commit.
6. `node "<review-cli>" record <ref>` -> `{ decision, handoff }`.
   - `decision.continue: true` -> go to step 1 for the next round.
   - If `record` returns `decision.intentReview`, print the handoff and stop: the run found changed lines that contradict stated requirements. These are reported, never auto-fixed. Resolve by editing the code (or correcting the design source) and re-running `/review-and-fix <ref>`; the re-run re-fetches the intent and re-reviews. A finding you judge a false positive needs no command -- read it, and merge by hand if you choose (concord never merges anything itself).
   - If `record` returns `decision.gatePending`, print the handoff and stop: the diff-local loop is clean, but broad review has open advisory findings (design/AC/cross-context) for a human. These are never auto-fixed. Resolve by fixing the code or the design source and re-running `/review-and-fix <ref>` (a fresh run re-evaluates broad review), or, for a finding you accept as out-of-scope/deferred, `review-cli.js dismiss <ref> <gateId>` so it stops surfacing. `gate-pending`, like a parked ledger, does not auto-clear -- re-run or dismiss.
   - If `record` returns `decision.dodFailed`, print the handoff and stop. Fix the reported DoD failure, then run `/review-and-fix <ref>` again; the ledger preserves the completed broad pass, reviews only the changed diff, and retries DoD only after that review converges.
   - Otherwise, `decision.continue: false` -> print the `handoff` verbatim and stop.

Never run more rounds than the CLI drives; the CLI enforces the round budget, the park-budget breaker, and convergence. A round is only real when its findings come from the subagents you spawned this session; if you ever find yourself reading a bot/CI/PR review to decide what to fix, or scheduling a wake-up to wait for one, you have left this loop -- stop and return to step 1. If a CLI verb exits non-zero with a `harness-failure:` message, stop and report it plainly -- do NOT characterize the run as clean or parked. A repo with no `review.config.json` is NOT one of those cases -- the run proceeds on the review gates alone and the handoff reports `DoD: DEFERRED`. Relay that deferral in your own summary too: never call such a run verified, and if the user wants a gate on future runs, point them at `{"dod":["node --test"]}` at the repo root (commit it -- an uncommitted config leaves the tree dirty and the next `round-start` rejects a dirty tree).

If a ledger for this ref is already `parked`, tell the user resuming will NOT auto-re-run parked findings; they must `review-cli.js unpark <ref> <findingId>` first. If the park has NO findings to unpark (a no-progress or budget-exhausted park -- e.g. the DoD kept failing with nothing for the review to fix), `unpark` has no target. A completed standalone disposition preserves its spent budget and evidence: after fixing the underlying cause, use bounded `rerun <ref>` rather than `reset`. `reset` is only for an incomplete standalone ledger with no recorded round. For an initiative-bound target, preserve the ledger and spent budget, report the blocker for reconciliation, and use `rerun <ref>` with the original initiative options only after that reconciliation. `rerun` never restores exhausted initiative budgets; do not reset or increase the budget to bypass exhaustion. Stop and report the printed `carry <ref> --from-run-key <old-key> ...` command for a human to run after reconciliation; never change the run key yourself, and never use `carry` to refresh context rather than recover a genuine budget block.

If the ledger is already `clean` and the user wants a SECOND review of the same ref -- typically with a different reviewer engine, for uncorrelated eyes -- use `review-cli.js rerun <ref> [--engine <name>]`, not `reset`. `rerun` archives the finished run (rounds, fix digest, kill rationales, gate ids) into the ledger's `runs[]` and re-arms it, so the next `round-start` drives a real round; the handoff reports every prior run. A completed front pass without an external intent source is reused across reruns while the resolved base and reviewed head ancestry still match, so the rerun reviews only the changed diff. Base drift, rewritten history, an intent-bound run, or explicit `--broad` invalidates that evidence and runs the front pass again. Once rerun history exists, `reset` refuses to discard it. The cumulative default is three full runs per target, including the initial run; after that `rerun` fails before changing the ledger or evidence. Treat that stop as a human reconciliation boundary: preserve unresolved findings and split scope or narrow the remaining verification instead of resetting state to repeat the full review. The new run starts blind on purpose: no findings are carried forward, because a second engine seeded with the first one's conclusions is no longer an independent look. `--engine <name>` is a free-text label recorded in the ledger and the handoff so the two runs are attributable.
