# Review until LGTM

Use this after implementation and ordinary local review are complete. It coordinates external automated PR feedback from Codex, Copilot, or another explicitly configured reviewer. It may fix, test, commit, and push review findings on the existing PR branch, but it never merges the PR, and it creates follow-up tickets only within the recorded tracker authorization.

Set `STATE_CLI` to the state script path before polling. A development checkout uses `plugins/concord/hooks/review-lgtm-state.js`; the optional Copilot shortcut is `${COPILOT_PLUGIN_ROOT}/bin/review-lgtm-state.js`. It is not required: use this Node-based locator, which searches only installed plugin caches and never the reviewed checkout, validates the Concord plugin manifest, and deterministically selects the newest installed Concord version: `node -e "const fs=require('fs'),p=require('path'),o=require('os'),q=[p.join(o.homedir(),'.claude','plugins','cache'),p.join(o.homedir(),'.codex','plugins','cache'),p.join(o.homedir(),'.copilot')],c=[];function a(f){let d=p.dirname(f);for(;;){try{const m=JSON.parse(fs.readFileSync(p.join(d,'.codex-plugin','plugin.json'),'utf8'));if(m.name==='concord'&&typeof m.version==='string')c.push([m.version,f]);return}catch{}const u=p.dirname(d);if(u===d)return;d=u}}for(const d of q){const s=[d];while(s.length){const x=s.pop();let z;try{z=fs.readdirSync(x,{withFileTypes:true})}catch{continue}for(const e of z){const f=p.join(x,e.name);if(e.isFile()&&e.name==='review-lgtm-state.js'&&['hooks','bin'].includes(p.basename(p.dirname(f))))a(f);if(e.isDirectory())s.push(f)}}}c.sort((x,y)=>x[0].localeCompare(y[0],undefined,{numeric:true}));if(c.length)console.log(c[c.length-1][1]);else process.exit(1)"`. Set its one-line output as `STATE_CLI`, then invoke every verb as `node "$STATE_CLI" <verb> ...` (PowerShell: `node $STATE_CLI <verb> ...`; cmd.exe: `node "%STATE_CLI%" <verb> ...`), never by executing the `.js` path. State lives in the repository git directory, keyed by PR number and exact head SHA, so interruption or session replacement does not reset a budget.

## Collect one head

1. Resolve the exact PR head SHA from the full `headRefOid`. Read only review objects, summary comments, threads, checks, approvals, and reactions attributable to that exact head; older-head feedback is history, not current evidence.
2. Run `node "$STATE_CLI" status <pr> <head-sha>`. When current-head matching activity first appears and `deadlineMs` is absent, run `node "$STATE_CLI" open-window <pr> <head-sha> 900`. The persisted 15-minute deadline bounds the whole collection, including in-progress reviewers and a completed review waiting for its signal.
3. Treat every automated reviewer explicitly requested on the PR or configured by the repository as part of the current-head batch. Do not start fixing when the first review arrives. Collect until every known automated reviewer is terminal. If GitHub does not expose a finite reviewer set, require 120 seconds with no new current-head review activity after the latest completion, still bounded by `deadlineMs`. Reaching the deadline with a known reviewer missing or in progress is `review-timeout`, not a complete batch or green.
4. If a configured reviewer has no matching activity, run `node "$STATE_CLI" claim-initial-request <pr> <head-sha> <provider-id>` for that reviewer. Use the stable reviewer login or configured provider name as `provider-id`; claims and sent markers are independent per provider. The first claim on a head starts a shared 120-second automatic-review grace and returns `auto-review-grace`; poll until `requestEligibleAtMs` so automatic reviews are not raced by manual requests. Request that provider only when its claim returns `{"claimed":true}`. Then run `mark-initial-requested <pr> <head-sha> <provider-id>` and `open-window <pr> <head-sha> 900`. `status.initialClaimed`, `initialRecoveryClaimed`, and `initialRequested` aggregate legacy and provider-keyed markers, including a legacy sent retry. On resume, if `initialRequested` is true but `deadlineMs` is absent, run `open-window <pr> <head-sha> 900` before polling. A provider claim without a sent marker has a 15-minute lease and may be recovered with `recover-initial-request <pr> <head-sha> <provider-id>` only after that lease. A finding from one reviewer does not block bounded claims needed to finish collecting the other configured reviewers. Reservation transitions are serialized per PR; retry `transition-busy` later, and treat a persistent lock as human reconciliation rather than reclaiming it automatically. Manual requests have a durable budget of three for the whole PR; legacy claims and sent-request markers count toward that budget, and a new head does not reset it. Stop on `request-budget-exhausted` and never delete markers, change the PR number, or start a new state directory to bypass it.
5. Normalize every current-head automated review before deciding. Map GitHub `APPROVED`, `COMMENTED`, `CHANGES_REQUESTED`, and `DISMISSED` reviews to `completed`; map pending provider activity to `in-progress`. Pass `reviewId`, `reviewer`, `reviewUrl`, the review's own full `commitId`, normalized `state`, `lgtm`, and all unresolved findings to `node "$STATE_CLI" record-review <pr> <head-sha>` on stdin. A finding contains its URL, P1/P2 priority when supplied or `null`, and applicable signals from `lifecycle`, `ledger`, `audit-privacy`, `provider-parity`, `ac-conflict`, and `unsupported-test`. Record every review in the collection batch even after one returns `needs-reconciliation`; never stop at the first reviewer and leave later feedback for another push.

An LGTM signal must be explicit and fresh for the current head: an automated GitHub `APPROVED` review, or that same reviewer's positive reaction on the PR itself created at or after its current-head terminal review or summary completion time, comparing timestamps at whole-second precision. Absence of findings is not itself LGTM. For Codex's clean no-review-object path, require no Codex review object for the full `headRefOid`, `status.reconciliation === null`, a `✅ Completed` summary row whose commit is a prefix of that head, and a `chatgpt-codex-connector[bot]` +1 reaction on the PR created at or after the row's completion time. A stale reaction never counts.

## Reconcile and fix one batch

An unresolved finding from any collected reviewer takes precedence over another reviewer's LGTM. Green requires the collection window to be complete, zero accepted current-head findings, and at least one fresh LGTM signal.

When findings exist:

1. Give the complete collected set to one clean-context verifier. It evaluates related or conflicting findings together, rejects false positives with evidence, deduplicates symptoms that share a root cause, and identifies repository-wide occurrences of the same pattern. Add a second independent verifier only for conflicting conclusions, security or data-boundary risk, or a proposed contract/architecture change.
   Seal that independent verdict before consulting approved design or prior fix history. In a separate planning pass, partition every accepted finding into exactly one explicit root-cause group; missing coverage, duplicate membership, or a legacy ungrouped plan stops before editing. Classify a shared root as structural when resolving it changes identity, ownership, retry accounting, ordering, idempotency, lease/fence, or deadline/TTL semantics. A structural auto-fix requires the exact approved source/hash, its normative requirements, and an explanation of why they determine one invariant-preserving answer. If the approved design uniquely determines that answer, authorize one structural fix for the complete group; otherwise stop before editing for human reconciliation and report every blocked group, all affected finding IDs, required invariants, and unresolved choices.
   Run `node "$STATE_CLI" reject-review-batch <pr> <head-sha>` only if the verifier concludes that every finding in the active batch is a false positive, passing the exact review ids and a non-empty evidence summary on stdin as `{"reviewIds":["..."],"reason":"..."}`. This durably preserves and disposes only that exact batch without claiming a fix round or creating an empty commit. It does not make the head green; fresh explicit LGTM evidence is still required.
2. Persist the versioned plan and bind its exact group membership, reviewed head, diff, approved-source hash, and owner to `claim-fix-round`. Reserve the complete batch before editing. A claimed fix round has one owner and ownership must not automatically transfer. If that owner or an initial fix claim is abandoned, stop for human reconciliation and confirm the former executor has stopped; do not reclaim it after a timeout. The three fix-and-push rounds are a PR-wide hard cap, not a quality guarantee; a new head does not replenish them. On `fix-round-budget-exhausted`, preserve the batch and stop for human reconciliation without claiming green.
3. Use a round-scoped transaction: apply every group sequentially in one isolated candidate, but publish nothing yet. An independent certifier then validates the final combined tree against every group member and invariant. Additive/shared-helper fixes are valid when behavior proves them; deleting quoted spans is neither necessary nor sufficient. Any incomplete member, stale target/design hash, changed candidate after certification, or failed check blocks the entire commit. Only the fully certified tree may become one commit and one push. Resolve or reply to review threads only after that push and its checks support the response.
4. Resolve the new full head SHA and repeat collection for that head only. Never request a second full review on the same head solely to obtain a missing reaction. If a terminal review has no findings and no fresh LGTM by `deadlineMs`, stop as `completed-without-lgtm`.

Stop instead of fixing when an accepted finding changes the approved product contract, materially expands the PR, requires unrelated architecture, or exposes a structural protocol choice the approved design does not settle. Also stop when three fix rounds do not converge. Do not keep changing the PR merely to obtain theoretical perfection; the residual findings go through the delivery disposition below.

## Delivery disposition

When collection for the exact head is terminal and no fix round is open, including after `fix-round-budget-exhausted`, classify the PR once with `node "$STATE_CLI" record-delivery <pr> <head-sha>`, passing the evidence packet on stdin: `{"baseSha","contractDigest","acceptance":[{"id","met"}],"requiredChecks":[{"name","conclusion"}],"reviewsTerminal","openChoices":[],"findings":[{"id","url","disposition","rootCause","releaseBlocking":[],"rationale","acceptedBy"}],"tickets":[{"rootCause","url","readBack","reused","duplicateCheck"}]}`. `contractDigest` is the SHA-256 of the approved contract. List every required check on the exact head; only `success` passes. List every accepted finding of every batch on the PR, fixed ones included, each with exactly one `disposition`: `fixed`, `follow-up`, `accepted` (by an authorized human named in `acceptedBy`), or `blocking`.

A finding is release-blocking when it falls in any of `acceptance-criterion`, `required-check`, `correctness`, `security`, `data-integrity`, `contract-choice`, `compatibility`, `contradictory-docs`, `unproven-premise`, or `stage-exit`; record those categories in `releaseBlocking`. A release-blocking finding blocks unless it is `fixed`, whatever the remaining budget. A finding is follow-up eligible only when it has no such category and its `rationale` says why the approved outcome, required checks, safety boundary, and documented behavior stay correct without it; priority labels and "ran out of rounds" are not reasons. Group follow-up findings by root cause and independently testable outcome, not one ticket per comment. When tracker mutation is authorized, create or reuse one implementation-ready ticket per root cause through `ticket-writing`, read it back, and set `readBack`. Reuse an existing ticket only after a duplicate check shows it carries the same outcome and scope, and record that check in `duplicateCheck`. Then link the source PR and each finding's review thread to the read-back ticket URL. Without authorization or access, omit the ticket: the CLI returns `rollover-pending` with a ready-to-file packet for the group, and no ticket URL is invented.

The CLI returns `mergeable-clean`, `mergeable-with-follow-ups`, or `blocked` with every reason. `status.delivery` reports the latest record for the head; while it is `mergeable-*`, request and fix claims return `delivery-terminal`, so reopening the unchanged head reports the stored result and launches no reviewer or fixer. A new commit is a new head. On resume, compare the live base, approved contract, and required checks with `status.delivery`; on any change, record the new evidence before acting. A `blocked` record re-enables claims. `mergeable-*` is not merged and not LGTM: never report `mergeable-with-follow-ups` as clean or green.

## Handoff

Report the PR, exact head, configured reviewers observed or missing, collection deadline, each recorded review's id, reviewer, URL and findings, fresh LGTM evidence, accepted and rejected grouped findings, active fix owner when work remains, checks run, commits pushed, and both budgets' max, spent, and remaining values. A timeout, exhausted budget, scope escalation, or `completed-without-lgtm` remains visibly not green. Also report the delivery classification with its exact head and base, required checks and their conclusions, each finding id with its disposition (fixed findings separately from current follow-ups), follow-up ticket URLs or pending packets, whether the PR and thread links are posted, and every blocking reason.
